the policy unit is **OS image + VM shape**, not hostname.

## Success criteria from issue #27 and how this lane meets them

1. **Register set and pinned expected values.** Registers: `MRTD`, `RTMR0`,
   `RTMR1`, `RTMR2` (RTMR3 is already replayed from the cc-eventlog). Pinned in
   `verifiers/aci_boot_registers.json` (schema `aci-boot-registers/1`) keyed by
   `os_image_hash` + VM shape. Provenance recorded in the file: values derived
   with dstack-mr 0.6.3 at dstack-TEE/dstack commit `d7e15dc` (branch `next`,
   2026-11-05), `Machine::measure()` mirroring dstack's own verifier
   (`dstack/verifier/src/verification.rs::compute_measurements`), from the OS
   image archive `https://download.dstack.org/os-images/mr_bd369a8c….tar.gz`
   (image `dstack-0.5.9`, git_revision `e3655d13`), with the deployment's
   authenticated `vm_config` (cpu 32, 34359738368 B, qemu 8.2.2, pci_hole64 0,
   no hugepages/GPU/nvswitch, hotplug on, 9p). Derivation ran on zed on
   2026-11-05; harness source retained under `research/dstack-mr-derivation-2026-11-05/`.
   Copying observed registers from evidence `01680c7c…` into the expected set
   was NOT done: the harness computed all four registers from the downloaded
   image before any comparison; the observed quote body matched afterward.
2. **Authenticated quote body compared against the set, obligations distinct.**
   New scorecard layer `boot_registers_match_pinned`, computed only when
   `tdx_verified` (Phala authenticated the quote whose body carries the
   registers). Boot-image obligation = this layer + the existing
   `os_image_archive_declares_production` and RTMR3 `os-image-hash` event
   binding; compose obligation = `compose_hash_committed`; keyset obligation =
   `report_data_binds_key` (+ endorsement when present); selected-backend
   obligation = `attested_serving_enforced`. `prod_os_image` becomes
   `boot_registers_match_pinned and os_image_archive_declares_production`
   instead of always-None.
3. **Replay + negative controls** (tests against retained evidence
   `data/observations/evidence/sha256/01680c7c….json`):
   - replay real event log / quote body / keyset / compose → accepted layers;
   - mutate each of MRTD, RTMR0, RTMR1, RTMR2 independently → rejected;
   - mutate the pinned policy (one register) → rejected;
   - policy entry absent (genuine quote, unapproved image) → rejected with
     reason, never N/A;
   - VM shape field altered (cpu_count 33) → rejected, "shape not approved";
   - event-log/quote binding altered (RTMR3 replay mismatch) → rejected
     (existing controls kept);
   - hostname not in measured `tee_only_domains` → attested_serving False.
4. **Unapproved profiles are rejections.** No policy entry for the measured
   os_image_hash, or a served vm_config shape that no entry pins, is
   `verification_status: rejected` with an explicit reason; nothing reports N/A.

## Issue #18 ACI part

`details.tcb_status` is null because `verify_tdx_quote` reads
`quote.tcb_status` from Phala's `cloud-api.phala.network` response, which
contains exactly `header`, `cert_data`, `body`, `verified` — the source never
provides a TCB status (confirmed live 2026-11-05 against the retained quote).
Fix: verify the quote locally with `dcap_qvl.get_collateral_and_verify` (the
same library the NEAR adapter uses; `--extra nearai` is already synced by
`probe-daily.yml`) and retain `tcb_status` + `advisory_ids` in
`details.tdx_tcb` with the source noted. No fallback: a dcap-qvl error
propagates and is reported, never silently None.

## Negative controls for #18

- local TCB helper returning non-(UpToDate|OutOfDate) status is recorded
  verbatim and never coerced;
- helper raising (tampered/unparseable quote) surfaces as an error entry, not
  `None` and not a pass.
