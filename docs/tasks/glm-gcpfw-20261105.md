# GLM lane gcpfw — Track Google's signed GCP Confidential VM firmware endorsements (issue #33)

Epoch 1 spec, written 2026-11-05 before implementation. Parent issue:
`/home/amiller/api-glm-run-20261105/issues/issue-33.md` (fetched 2026-11-05).

## Scope decision

Existing tooling is `watch/firmware_endorsements.py` (daily tee-beat job): it lists
the `gce_tcb_integrity` bucket and diffs listings, but never downloads endorsement
contents and verifies nothing cryptically. Per the lane brief this work **extends
that family, not duplicates it**: a new sibling module `watch/gce_tcb_endorsements.py`
reuses the listing helper, downloads the small TDX endorsements (~5-6 KB each),
verifies them, and writes append-only history to `data/gce-tcb-endorsements.json`.

## Success criteria from the issue, and what I commit to

- **S1 Parse**: each `ovmf_x64_csm/tdx/<MRTD>.binarypb` parses as
  `cloud_vmm_proto.VMLaunchEndorsement` (gce-tcb-verifier schema, vendored at tag
  v0.3.1). Stdlib wire-format parser; no new dependencies.
- **S2 Signature chain**: `signature` is RSA-PSS(SHA-256, salt=32, MGF1-SHA256) by
  the leaf cert in `VMGoldenMeasurement.cert` over `serialized_uefi_golden`
  (upstream `verify.EndorsementProto` + `OpensslVerifyShellCmd` semantics). Leaf
  cert chains to the vendored root
  `https://pki.goog/cloud_integrity/GCE-cc-tcb-root_1.crt` (DER, fetched
  2026-11-05, SHA-256 fingerprint E8:76:BC:…:8C recorded with the bytes).
  Additional binding beyond upstream: `ca_bundle[0]` DER must equal the vendored
  root DER, so a Google-side chain change fails loudly instead of silently.
- **S3 MRTD/name binding**: the object-name MRTD must be among the endorsement's
  `tdx.measurements[].mrtd`.
- **S4 Firmware digest binding**: `ovmf_x64_csm/<hex(digest)>.fd` must exist in
  the same bucket listing. One live 2 MiB `.fd` download cross-checks
  sha384(content) == endorsement digest == object name; result recorded in the
  history file (not committed as a binary fixture, per disk hygiene).
- **S5 History**: `data/gce-tcb-endorsements.json` records per MRTD: firmware
  sha384, golden timestamp, cl_spec/commit, SVN, measurements, signer cert
  (subject, SHA-256 fingerprint, validity), first_seen/last_seen (bucket
  timeCreated), per-check results, failure log. Withdrawals (objects present in
  history but absent from a later listing) are recorded, never deleted.
  `.fd` object history and `intel_rims/*` metadata (updated, generation, md5)
  are tracked so daily runs detect additions/removals/rewrites.
- **S6 Daily runnable**: `python3 watch/gce_tcb_endorsements.py` performs the full
  cycle online; `--lookup <mrtd>` resolves any MRTD to its endorsed build and
  age. I will not modify the live `beat-digest.sh` runner (deployment belongs to
  the owner); wiring is documented in the report.
- **S7 Provider rows**: retained TDX MRTDs in the repo (`data/audits/chutes_tee.json`)
  are cross-referenced against the endorsement set and flagged. Fact established
  today: both retained values are NOT GCE-endorsed (Chutes is a non-dstack custom
  TDX stack, `providers/chutes.md`).
- **S8 Negative controls** (each passing check must be proven to fail on tampered
  input, independently): tampered `serialized_uefi_golden` byte; tampered
  `signature`; wrong root; rogue signer not chained to the root; `ca_bundle[0]` ≠
  root; object-name MRTD absent from measurements; digest naming a missing `.fd`;
  cert not yet valid at the signed golden timestamp; missing provenance
  (post-2024-08-02 timestamp with no cl_spec/commit); truncated/garbage protobuf.
  Synthetic tampering uses a test-generated mini RSA-PSS CA so each mutated input
  is independently constructible; real retained endorsements cover the positive
  path.

## Criteria I cannot meet (precise blockers)

- **"For every provider row on GCP TDX, record which endorsed build its quote
  shows"**: the repo has no GCP-TDX provider row with a retained quote. The
  issue's dstack GCP test VM observations (Sept/Nov 2026) are not in
  `data/observations/`. Delivered instead: the lookup/flagging machinery (S7) and
  the fact that current retained TDX MRTDs are unendorsed by GCE.
- **"How long after an endorsement is published do hosts run it?"**: needs
  repeated host-side MRTD observations, which do not exist in this repo.
- **AWS/Azure equivalents**: different lanes (#18 tracks Intel TCB status);
  out of scope here.
- **intel_rims content diff**: epoch 1 tracks metadata (md5/generation/updated)
  and reports changes; retaining full textproto contents on change is deferred
  to a later epoch. **[Closed later in epoch 1]**: `retain_rim_contents` now
  downloads and stores each new/changed rim version under
  `data/gce-tcb-intel-rims/<base>/<md5>.textproto`, verified against the
  listing md5; fixtures and tests added.

## Evidence sources (independent of the values being checked)

- Root certificate: fetched from pki.goog (DER bytes + fingerprint recorded);
  vendored under `tests/fixtures/gce-tcb/`.
- Endorsement fixtures: 4 real objects captured 2026-11-05 from
  `https://storage.googleapis.com/gce_tcb_integrity/...` covering the 2024
  multi-measurement era, a mid-2024 rotation, and both 2026-11-04 newcomers.
- Listing fixture: today's full `ovmf_x64_csm/` name listing for `.fd` binding.
- Schema reference: gce-tcb-verifier v0.3.1 `proto/endorsement.proto` and
  `proto/certificates.proto`, vendored with URL and tag.
