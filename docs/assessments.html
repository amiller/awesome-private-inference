Route assessments

Dated explanations of what is established, what is missing, and which operator powers remain relevant. These are preliminary source/evidence reviews, not completed end-to-end devproof audits.

Assessment obligations · version 2

A route is a named client mode, recipient and model path. Plaintext inside approved attested code does not imply operator access. The question is whether an operator can obtain it or alter the computation without the client refusing.

Each cell names a concrete finding or task. “Our … missing/pending” identifies unfinished verification or evidence in this repository. It is not evidence of a provider defect. Select a cell for what was checked, what remains to prove, and a linked issue with acceptance tests.

Work in our verifier
A required check is absent or incomplete in our implementation, such as AMD report-signature verification or GPU appraisal. The linked task states what an implementation and rejection tests must establish.
Evidence we still need
A route-specific test, build reproduction or current review has not been retained. This is unfinished assessment work, not a finding that the provider lacks the protection.
Finding in the reviewed system
A dated source review or experiment identifies a specific protection boundary, such as unmeasured serving code or a substitutable reply key. Read the exact client/version and evidence scope before applying it to another deployment.
Scope of this route
A standard or retention-only path makes a different claim from client-verified confidential inference. It cannot inherit the guarantees of a separate encrypted path.
Routes differ
The provider has distinct client paths or unresolved obligations. Expand its row or follow the cell; no best-route selection or averaging is performed.

Collection is independent: “returned” includes responses an adapter rejected or could not fully check; “unavailable” means no usable response; “stale / mixed” includes samples more than 48 hours older than the snapshot. Exact observation dates and every raw check are on Measurements.

Assessments remain dated source findings as references change. Provider-wide reference differences from the retained review baseline flag re-review; they do not automatically rewrite the assessment or expand accepted policy. A changed document may be unrelated to a particular route. Follow its history and trace the dependency before assigning impact.

Promotion requires a recorded reviewer, exact client and workload versions, linked proof records and reproducible negative controls. No overall security stages are assigned. Existing internal states are retained without promotion; visible labels describe the actual work or finding. Dates refer to source review, not fresh deployment certification.

Hardware

Is platform evidence authenticated under the relevant hardware and TCB policy?

Authenticate the vendor-root chain, quote signature, TCB/debug policy and any GPU evidence required by the route. Release-signature verification alone is insufficient. Changed signatures and unacceptable TCB must reject.

Session

Are prompt recipient, reply key and freshness bound to the actual client exchange?

Bind the live channel, prompt recipient, reply key and freshness before sensitive data leaves the client. Test key replacement, replay and reply-key substitution. A receipt after disclosure is insufficient.

Code

Does measured workload identity resolve to approved, reproducible source?

Trace source, build, artifact and measurement to the approved workload, including serving code and model identity where claimed. Distinguish reproducibility from signed provenance and matching digests.

Operator access

Are operator-controlled inputs and access paths constrained by the approved computation?

Trace root/debug access, unmeasured configuration, secrets, control-plane inputs and mutable routing to actual effects on prompts and replies. A configuration finding is specific to the reviewed code and deployment.

Downstream

Are required worker hops and the requested model bound to the verified request?

Close necessary gateway-to-worker trust links and requested-model mapping. Test substituted workers, models and route fallback. A direct route can eliminate a gateway hop but still needs its model proof.

Updates

Can the client reject changes to accepted code until its approval policy authorizes them?

Identify who changes accepted values and when the client adopts them. Test an unapproved release, rollback and manifest update. Automatic adoption and independently reviewed pins imply different authority.
