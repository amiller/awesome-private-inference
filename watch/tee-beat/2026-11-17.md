## Code and releases

- **Dstack-TEE/dstack — one-off KMS cluster-merge release, new to the record**:
  [kms-v0.6.5-mrgk](https://github.com/Dstack-TEE/dstack/releases/tag/kms-v0.6.5-mrgk)
  (published 2026-11-17T04:41Z, source branch `release/0.6.5-mrgk`, PR #1594).
  Explicitly labeled "one-off build, not a regular release": joins the roots
  of two independently bootstrapped KMS clusters into one keyring — the
  surviving cluster keeps epochs `0..N-1` and the other cluster's root is
  imported as epoch `N`, byte-identical derived keys for the imported apps.
  `Onboard` gains `merge_source_url`/`merge_source_token`; onboarding refuses
  without storing anything when the merged keyring does not match registered
  chain hashes, the merge source holds more than one epoch, or either source
  is not authorized. Merge logic is not in `next` or any later release.
- Dstack-TEE/dstack: [PR #1595](https://github.com/Dstack-TEE/dstack/pull/1595)
  "feat(kms)!: archive each root epoch's attestation and move the keyring to
  keyring_dir" (merged 2026-11-17T04:16Z, breaking). Key handover now carries
  the attestation produced at each root epoch's generation (`KmsKeys.attestation`,
  archived unverified — relying parties verify); per-epoch layout
  `<keyring_dir>/epochs/<n>/…` replaces the overwritten `bootstrap-info.json`
  (`GetMeta.bootstrap_info` reports the served epoch's attestation); keyring
  moves from `cert_dir` to `core.keyring_dir` and all mutable KMS state
  defaults to `/var/lib/kms`, leaving `/etc/kms` to configuration. Fixes loss
  of older-epoch evidence on rotation/join. Follow-up commits default the KMS
  state paths and update tutorials to a single `kms-data` volume. No new
  release carries it yet.
