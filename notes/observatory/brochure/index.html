Private Inference Observatory

Every private inference client decides what to trust by comparing an attestation against a list of reference values. Since April we have recorded, every day, what the providers publish, what their machines actually attest to, and what each client accepts. The observatory we propose keeps that record going and makes it usable, so that a client can trust only values that have been public for a while, and anyone can settle later what was running and whether it was acceptable at the time.

Gateways change identity every few days, while the model enclaves behind them barely change

Each row is one attested component, and each tick is one day of our daily probe. A dark tick marks a day the component reported an identity we had never seen before: a new image digest, measurement or compose hash. The router and gateway layers, which sit closest to the operator, turn over constantly. The enclaves that actually decrypt prompts go months without changing. A client that pins a gateway value goes stale within a week, which is why pinning alone doesn't work.

The first day we see a value is not the day it was deployed, since a long-running machine may simply be sampled for the first time. The Chutes Qwen3-32B row shows why we mark returns separately: it has exactly two measurements and alternates between them because a load balancer is being sampled once a day. A naive change count would rate the most static fleet in the registry as the most volatile.

NEAR's gateway firmware was out of date in every quote we kept from April to October

Whether a firmware level is acceptable depends on the date. A level that is current in May becomes out of date once Intel publishes a newer one. Because we kept every NEAR gateway quote, we could rate each one afterwards against Intel's dated TCB history.

Rated with dcap-qvl against Intel's TCB evaluation data. Dots are saved captures, bars are daily checks, and 9 and 4 are the advisory counts. The two old levels alternate, which points to two gateway hosts. Our Abalone client stopped trusting the gateway on Oct 23 and pinned one model machine through NEAR's Direct endpoints. NEAR moved the gateway to new firmware the next day.

NEAR's deployment log now keeps seven days, so the archive is the only long record of what each machine ran

Each NEAR model machine runs a deployment service that logs every container it starts and stops, and binds the log to the machine's attestation. That log is the only record of which serving code a machine ran. Since Nov 13 it is pruned to seven days, and NEAR's own pull request says a verifier "has to keep its own copy". We now keep one raw capture per machine per day, about 70 MB a year. Each dot below is one logged action, recovered from that archive and from earlier captures back to September.

The opinion beside each machine comes from our audit this month. It depends on how each container image is named. A digest resolves from the log alone. A tag resolves through the registry's history. An unpinned pip build resolves by replaying PyPI's public upload history at the build date, which left a reviewer 61 packages to read on gpu23. A private image cannot be resolved from outside at all.

None of the 76 client-provider pairings we graded verifies the code that reads the prompt

We reviewed every third-party client we could find that checks attestation for private inference, at a pinned commit. Each cell grades what that client establishes against that provider. "Partial" means it checks real evidence but stops short of the serving code or doesn't block the request. "Weak" means little is authenticated. No cell reaches "serving", which would mean the client checks the code that reads the prompt and blocks the request if that check fails. This grid is the Awesome Private Inference tab.

Most clients adopt the provider's latest reference values automatically. teep and NEAR's gateway take the newest Sigstore-signed router release, tinfoil-go takes any release Tinfoil signs, and Privatemode takes any manifest its CDN serves, unsigned. In effect the client trusts whoever writes the list, which is reasonable only if somebody is watching what gets published.

The record exists to make a transparency policy workable for reference values

Certificate transparency solved a version of this problem for TLS. A browser accepts a certificate only if it appears in a public log, and independent monitors read the logs for certificates that shouldn't be there. Private inference has the logs already: Tinfoil releases go to Sigstore, and NEAR adds compose hashes on chain. What it lacks is the monitor, and the observatory is meant to be that monitor.

Published, observed and accepted are separate records

On Oct 12 a Chutes instance returned a valid, current quote whose measurement matched none of the 55 published rows. It was a golden-set value that had since been withdrawn. Chutes' published set now has 62 rows, and none of them varies by model, so the published values constrain the base VM and not the serving code.

Some evidence exists only if someone keeps it on the day

Pruned deployment logs, git tags that can be moved, firmware ratings that depend on the date: none of these can be reconstructed later. Authenticated history is whatever somebody fetched with their own nonce at the time.

Expected values can be derived without the provider

Our dstack-mr derivation computes a dstack OS image's boot measurements without starting a VM, and PyPI's public history pins what an unpinned build resolved to. Where we have not done a derivation yet, the gap is ours, and the site reports it that way.

The observatory has five goals

Keep the record

Retain published, observed and accepted values with dates and raw evidence, per machine wherever the provider exposes machines.

Support transparency policies

Export observed values with first-seen times so that clients can diff their allowlists and require a waiting period.

Derive expected values

Compute measurements from source, resolve image names to bytes, and list the values nobody outside the provider can derive.

Rate routes and verifiers

Private Inference Beat applies stage criteria to each request path, in the manner of L2BEAT. Awesome Private Inference tracks the verifiers.

Let clients act on it

A client should be able to choose a provider or machine from what the observatory has seen, and switch when the evidence changes.

Running it takes one compute host, provider accounts, and a reviewer's time

  • Per-machine archives for every fleet. The NEAR collector generalizes to Tinfoil, Chutes and the Phala gateways, at roughly 1 MB of JSON a day per fleet.
  • Funded API accounts. Credentialed tests of each request path need a paid key per provider. This is the largest gap in coverage today.
  • Independent derivations. Boot measurements for the gateways, AMD signature chains, and source-to-image rebuilds.
  • Outside checks on ourselves. A separately hosted heartbeat, a target of at least 95% of scheduled runs recorded over 30 days, reader testing, and eventually a tamper-evident log.
  • Review. Agents draft the change reports, and an informed person decides. Most open cells on the site are our own unfinished checks, so reviewer time is the real limit.

We assume the CPU vendors' hardware roots of trust are sound. NEAR's Direct endpoints, which let a client choose a machine, close on Dec 6. After that the archived evidence remains, but it can no longer steer a request. That is one reason to record continuously rather than audit once.
