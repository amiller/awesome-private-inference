Private Inference Observatory

A private inference client decides which software to trust by comparing an attestation against a list of reference values, and today that list is written by the provider, adopted by the client automatically, and rarely checked against what actually runs. The observatory we propose keeps an independent, dated record of every reference value that was published, observed in a live attestation, and accepted by a client. Its goal is to make a transparency policy workable: a client should be able to accept only values that have been public for a while, and anyone should be able to settle later what was running and whether it was acceptable at the time.

Attestation moves trust from the provider's machines to whoever writes the reference list

Start with what a careful client does. It sends a fresh nonce to the inference machine and gets back a quote, a statement signed by the CPU vendor's key that reports the machine's measurements (boot firmware, kernel, the compose file that lists its containers) along with the nonce. The client checks the signature chain up to Intel, AMD or NVIDIA, checks the nonce, and then compares each measurement against a list of expected values. If they match, it sends the prompt.

The first two checks are mechanical, and in the first 111 days of our daily runs they recorded no verification failures. The third check is where the decision is made, because the signature only proves that the machine is running some measured software. Which software is acceptable is whatever the list says. So the question becomes who writes the list and how a client gets updates to it. In the 50 verifying clients we reviewed, the usual answer is that the provider writes it and the client takes each new version without asking:

  • teep and NEAR's gateway accept the latest Sigstore-signed router release.
  • tinfoil-go accepts any release or policy Tinfoil signs.
  • Privatemode accepts any manifest served from its CDN, over plain HTTPS, unsigned.
  • Maple's signatures cover the PCR0 text only, not PCR1 and PCR2, their order, or their retirement.

A client like this has trust-on-first-use, with the first use delegated to the list's author. That is a reasonable design, as long as somebody is watching what the author publishes.

Pinning breaks on every redeploy, so a transparency policy needs a monitor

The obvious alternative is to pin: write the expected values into the client and refuse anything else. One of our own clients did this against a Phala gateway, and it broke the next time the gateway was redeployed and its compose hash changed. Our observations show why. The router and gateway layers of these services get a new identity every few days, while the per-model machines behind them stay almost static. Any client that pins the outer layer goes stale within a week.

That's really unacceptable rigid pinning, we know the data on how often they do this because of our observatory awesome-private-inference. We have to be more robust.
Andrew Miller, 2026-11-22

The middle path is the one certificate transparency took for TLS. A client accepts a value only if it appears in a public, timestamped log, optionally after a waiting period, so that a bad release has to sit in public view before anyone trusts it. Most of the pieces already exist. Tinfoil's releases go to Sigstore's log. NEAR's compose hashes are added on chain with an addComposeHash call, so a client can require that a hash has been on chain for some minimum time. Seen this way, the gap between providers is mostly a difference in client policy. But a log only protects anyone when someone reads it. In certificate transparency that job belongs to monitors, which watch the logs for certificates that shouldn't be there. The observatory is meant to be that monitor for private inference.

Published, observed and accepted values are three records that often disagree

The observatory keeps the three apart. A value appearing in a publication says nothing about whether any machine runs it. A value appearing in a quote says nothing about whether the provider approved it or any client accepts it. The daily export, reference-values.json, says this in its own policy field: it is a read-only feed of observations and must never be used as a client allowlist. The first time we see a value is also not the time it was deployed, since a long-running machine may simply be sampled for the first time.

Keeping the three records separate is what makes disagreements visible:

  • Chutes. On Oct 12 an instance returned a valid, current quote bound to our nonce whose MRTD matched none of the 55 published rows. It was an older golden-set value that had since been withdrawn. We had not kept the raw quote, so the case cannot be replayed today, and the observatory now retains raw quotes for exactly this reason. Chutes' published set has grown to 62 rows over four base-VM versions, and none of the rows varies by model or image. The published values constrain the base VM, not the code that serves a given model.
  • RedPill. Its Chutes verifier reads no MRTD or RTMR at all. Its policy for dstack upstreams pins app IDs, KMS roots and the compose hash instead.
  • teep. teep's allowlist lagged NEAR's Nov 4 OS measurements (teep#233). The export exists so that teep and other clients can diff their allowlists against what is actually being served.

Some reference evidence exists only if someone keeps it at the time

NEAR runs each model machine with a deployment service (compose-manager) that keeps a log of every container it has started, and binds the log to the machine's quote. That log is the only record of which serving code a machine ran. Since Nov 13 the service prunes the log to seven days, and NEAR's own pull request says a verifier "has to keep its own copy". Authenticated history is whatever somebody fetched with their own nonce on the day. Git tags, which name many of the images, are not a transparency log either, since a tag can be moved. So the observatory now keeps one raw record per NEAR machine per day: the quote, the deployment log, the TLS certificate fingerprint and the TCB status. That costs about 70 MB a year for the fleet.

TCB status is the clearest case of a reference value that changes with time. Whether a firmware level is acceptable depends on the date: a level that is current in May is out of date once Intel publishes a newer one. Because we kept every NEAR gateway quote from April onward, we could rate each one against Intel's dated TCB history afterwards. Every quote from April to October was out of date.

Whose minimum applies is a reference value too. Tinfoil's router reports AMD SEV-SNP firmware 0x17 and 0x1B. AMD's November bulletin sets 0x1D as the minimum, while teep and tinfoil-go accept anything from 0x0E. All of these are reasonable to publish, and a client should know which one it is applying.

How an image is named decides whether an outsider can derive its reference value

A compose file names each container image, and the measurement covers the name, not the image's contents. To say anything about the code, someone has to resolve the name to bytes. Auditing five NEAR model machines this month, we found that each way of naming an image takes a different amount of work to resolve:

Image named byWhat resolving it tookMachine
DigestThe deployment log alonegpu02, gpu04
TagNVIDIA's catalog shows the tag was pushed Feb 12 and never movedgpu03
Unpinned pip buildReplaying PyPI's history at the build date, plus Docker's cache rulesgpu23
Source buildAn offline rebuildgpu23
Private imageNothing works from outsidegpu13

The pip case shows that a public package index can serve as a reference anchor. The build inside the VM installed unpinned packages, but PyPI keeps a public, dated record of every upload and removal. Given the package names and the build date, the set that pip would have resolved is determined. One of them, fastapi 0.162.0, had been uploaded 3 minutes 18 seconds before the build ran. A scan of 3.5 million PyPI changelog events found that no file the build could have used was later removed. That leaves a reviewer with 61 distributions to read, 177 MB compressed. Following this standard, we reached a positive opinion on three of the five machines and not on the other two, which means a client following the same standard would route to some NEAR machines and avoid others.

Some expected values can also be derived without the provider's help. Our dstack-mr derivation computes the boot measurements of a dstack OS image without starting a VM. Where we have not done the derivation yet, as for the NEAR gateway's RTMR0, the missing check is our gap and not the provider's fault, and the observatory reports it as our unfinished work.

The observatory has five goals

  1. Keep the record. Retain published, observed and accepted reference values with their dates and raw evidence, per machine where the provider exposes machines, so that a later question about what ran can still be answered.
  2. Make transparency policies practical. Export observed values with first-seen times so clients can diff their allowlists and require a waiting period. Archive the things that are not logs today, like git tags and pruned deployment logs.
  3. Derive expected values independently. Rebuild or compute measurements from source, resolve image names to bytes, and record which values nobody outside the provider can derive.
  4. Assess routes against stated criteria. The Private Inference Beat tab applies proposed stage criteria to each request path, in the manner of L2Beat. The Awesome Private Inference tab tracks every third-party verifier and what it actually checks.
  5. Let clients act on it. A client should be able to choose a provider or a machine based on what the observatory has seen, and switch when the evidence changes. Our own client's Oct 23 move to a single directly attested NEAR machine is the first case.

NEAR's Direct endpoints, which let a client choose a machine, close on Dec 6. After that the audit data stays available, but it can no longer steer a request, and nobody outside NEAR can confirm the machine list is complete. Recording changes like this as they happen, while they can still be checked, is the reason to run the observatory continuously rather than auditing once.

The rest of the work is described in the companion brochure: a per-machine archive for every fleet, funded API access for credentialed tests, an independent heartbeat, reader testing, and a tamper-evident log. Throughout, we assume the CPU vendors' hardware roots of trust are sound.
