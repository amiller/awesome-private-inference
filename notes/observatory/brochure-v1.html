Proposal · November 2026

Private Inference Observatory

Confidential inference providers change the software their clients trust every few days, and the clients mostly accept whatever they are shown. We propose an observatory that retains each provider's attestation evidence over time and reviews what it does and does not establish. The goal is that a client author, a provider, or a user choosing between them can check what a privacy claim rests on.

A client's attestation check passes, while the exposure sits outside what it checks

We started in April 2026 by running daily attestation checks against the TEE inference providers, much like a careful client would. Over the first 111 days the checks recorded zero verification failures across 2,358 provider-model-days. Every red cell on our dashboard turned out to be network weather: timeouts, 503s, rotated endpoints. We now report reachability and verification separately.

Everything that actually mattered for confidentiality was found next to the quote rather than in it, by reading code and retaining evidence:

  • Chutes excludes serve.py and chute.py from measurement, and we demonstrated cross-user prompt exfiltration from an enclave that reported verified=True (chutes#75).
  • NEAR's compose-manager deploys serving code after boot from git tags with no minimum age. Production machines ran personal-branch and experiments/ files (compose-manager#85).
  • Brave Leo verifies NEAR thoroughly on Brave's server, but the browser's "Verified" badge is hardcoded, and the attested recipient is NEAR's gateway, not the model machine.
  • Tinfoil's router accepts an unsigned runtime config that assigns customers to replicas, and its control plane can rewrite model:"auto" request bodies.
  • Of 50 third-party verifying clients we reviewed at pinned commits, reply authenticity was the weak point in nearly all of them, and most adopt the provider's latest release automatically.

Our own verifiers had the same problems. An offline counterexample made our ACI adapter accept a quote with mismatched report data, and an outside reader showed that our bar for Venice left out two layers it should have required. The observatory has to audit its own instruments as well as the providers.

NEAR's gateway shows what a retained timeline settles that a single check cannot

The clearest example is this month's NEAR fleet audit. We kept every gateway quote we captured from April onward and checked each one against Intel's published TCB history. Every quote from April to October was rated OutOfDate under the Intel data current at the time. The gateway alternated between two old firmware levels, which points to two gateway hosts with traffic landing on either. A one-time check would have reported "OutOfDate today". The timeline tells us how long, on which hosts, and when the problem ended.

The same history explains a decision we had already made. On Oct 9 Abalone recorded the gateway as OutOfDate and ran NEAR only under an explicit firmware-warning trial policy. On Oct 22 we found that teep's gateway policy admitted the out-of-date gateway without flagging it. On Oct 23 Abalone stopped trusting the gateway and pinned a single model machine through NEAR's Direct endpoints, requiring UpToDate firmware and a reviewed boot image. NEAR updated the gateway firmware the next day.

Direct also let us judge machines one at a time. Following the same standard on each of five NEAR model machines, we reached a positive opinion on three and not on two. Each image is identified a different way: by digest in the log, by a tag resolved through NVIDIA's catalog, by replaying an unpinned pip build against PyPI's history, or not at all for a private image. Direct closes on Dec 6. After that the audit can still be run, but its result can no longer steer which machine a request goes to. Recording that change as it happens is another thing an observatory is for.

The instruments already running cover seven months of daily evidence

Daily attestation probe

GitHub CI, adapters for NEAR, Tinfoil, Chutes, Venice and the dstack/ACI providers. Every check reports verified, rejected, not_checked, unavailable or not_applicable. 212 daily snapshots since Apr 21.

Route and client registries

19 request routes, each naming who can read plaintext on that route. 50 verifying clients reviewed at pinned commits. 7 candidate providers on weekly review.

Reference publication monitors

Captures of Maple PCRs, the Privatemode manifest, the Confidential AI allowlist and the Private Inference bundle, so a changed reference value is recorded alongside the changed workload.

Daily beats

Two digests on zed each morning: provider and verifier news, and TEE platform news (Intel, AMD, NVIDIA, GCP firmware endorsements). They caught NEAR's SGLang RCE and Phala's 18-day prompt exposure on an OpenRouter route.

Review queue

Detected changes become leased review jobs, drafted by agents and published only after review, with a retry budget. One reviewed decision is published so far.

NEAR machine logbook

New this week: one archived record per NEAR model machine per day, with quote, compose-manager log, TLS binding and TCB status, about 70 MB a year.

Running it takes one compute host, provider accounts, and a reviewer's time

  • Compute and storage. GitHub Actions and Pages for the daily probe and site, plus one server (zed today) for builds, teep runs, beats and review agents. Storage is small: about 1 MB of JSON a day per fleet.
  • Provider access. A funded API account at each provider for credentialed tests. This is the largest open dependency and the one that most limits coverage today.
  • Model budget. Two daily beat digests and a review agent per detected change.
  • Review. The judgments that matter, such as whether a bar is right or an unpinned build is acceptable, still need an informed person. Agents draft and humans decide. Most of today's open cells (about 150 of 190) are our own unfinished checks, so review time is the real limiting cost.
  • Outside readers. Providers and client maintainers have acted on findings (NEAR fixed the May model substitution in cloud-api #708 and merged our compose-manager PRs), and an outside reader corrected our Venice bar. The observatory works best with those channels kept open.

We have not priced these yet. API credits and model usage are the variable costs; the host and storage are already paid for.

The observatory answers one question per route, for whoever relies on it

For a particular client, model and request path: who can read protected data, what evidence limits that access, and who can change the software the client accepts? Client authors such as teep, Abalone and bitrouter get reference values and known failure cases to test against. Providers get specific, reproducible reports. A user choosing a provider gets an account that separates what was observed, what the provider authorized, what was reviewed and what a given client actually accepts. A "rejected" cell means our verifier rejected the evidence within its stated scope. It does not mean the provider was compromised. We also assume the hardware roots of trust are sound.
