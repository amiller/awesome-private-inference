# Who can read prompts today on Tinfoil, NEAR AI, and Phala/RedPill — 2026-11-04

Prepared for the question "only Tinfoil is good?". Evidence cutoff 2026-11-04. Claims carry primary links and dates; secondhand or inferred items are marked. No live probes were run: this note reads this registry's retained evidence, the companion [DevProof audits](https://github.com/amiller/devproof-audits-guide), and provider sources fetched 2026-11-04 (treated as untrusted data).

## Answer

No provider, on any path, gives a default client a completed proof that prompt plaintext is invisible to the operator — the honest differences are in how tightly operator power is constrained and what the client must verify. On **Tinfoil**, the plaintext holders on the audited deployment were the router and model enclaves only, and the 2026-04-26 audit traced every operator-controllable config slot off the prompt path ("zero on the prompt path"); but this registry has never authenticated Tinfoil's AMD SEV-SNP signature chain (our gap, [issue #26](https://github.com/amiller/awesome-private-inference/issues/26)), that trace predates the 2026-07-16 move of serving config to Tinfoil's control plane, and two enclaves were never audited — an audited-and-since-changed claim, not a verified-today one. On **NEAR**, the ordinary gateway path has gateway and worker as plaintext holders with no client-side request-path proof; the E2EE path removes the gateway from protected-field decryption only when a verifying client pins the attested key — and reply confidentiality is broken independently by [cloud-api #1061](https://github.com/nearai/cloud-api/issues/1061) (open since 2026-09-14, no linked fix), while server-side compose enforcement still has no evidence; with a closed-chain client NEAR was rated Stage 1 alongside Tinfoil from 2026-05-05 through 2026-08-18. On **Phala/RedPill**, "Phala" is two things — dstack, the substrate NEAR also runs, and the hosted ACI service — and the ACI protocol verifies cleanly live (quote, keyset, measured compose, TLS, receipts on 2026-08-13/18), but the deployed service keeps Stage-0 findings and api.redpill.ai routes to non-TEE backends that "can see the prompt" per RedPill's own docs. "Only Tinfoil is good" is defensible about Tinfoil's *audited deployment and verifying SDK*; "Phala and NEAR are also state of the art" is defensible about *architecture*, not about either deployed service or either default client. The August stage table was removed on 2026-10-13/14 because brand-level stages mixed exactly these things (see §3–4).

## 1. Who can read plaintext, per provider and path

### Tinfoil (direct route; the only path this registry tracks)

Route `tinfoil-router`: client → router enclave → model enclave. EHBP encrypts bodies to the attested key but "preserv[es] routing metadata" — method/URL/headers remain visible to the router ([docs.tinfoil.sh](https://docs.tinfoil.sh/resources/ehbp.md), undated, fetched 2026-11-04; route in [data/routes.json](../data/routes.json)).

- **Evidence (2026-04-26, live deployment):** the [DevProof audit](https://github.com/amiller/devproof-audits-guide/blob/main/case-studies/tinfoil-confidential-inference/DEVPROOF-REPORT.md) verdict: *"**Stage 1.** The audit applied the prompt-path test to every operator-controllable slot in the live deployment and found zero on the prompt path."* The router's two external slots (`DOMAIN`, `USAGE_REPORTER_SECRET`) were traced off the prompt path by source (inferred, not demonstrated live); model enclaves verified zero external env and zero secrets; two enclaves (`deepseek-v4-pro`, `kimi-k2-6`) were unreachable and never audited.
- **Provider changes since:** config moved from public per-model repos to Tinfoil's control plane (2026-07-16); an attested safeguards classifier added to the chat path (2026-09-15) — it reads plaintext inside an enclave; the router now verifies downstream enclaves itself (#502, 2026-10-12); chat moved off the router (#533, 2026-11-01). The V3 attestation stack ([beta](https://docs.tinfoil.sh/resources/feature-status.md), tinfoil-go merges 2026-09-30 → 2026-10-08) adds what April lacked: AMD VCEK→ASK→ARK chain validation with embedded roots, a client-supplied nonce, and freshness witnesses ≤7 days. TLS pinning became the SDK default (2026-11-02), after a fix for dialers silently skipping the pin (2026-10-28). GPU attestation is boot-time only. No post-April third-party audit was found.
- **What limits the claim today:** our adapter does not authenticate the SEV report signature — hardware axis "unknown · our AMD check missing" ([data/assessments/routes.json](../data/assessments/routes.json), reviewed 2026-10-14); the operator-input trace predates the July config move; no live encrypted request ever completed by this registry; the router lane has alternated between two instance shapes since 2026-10-27 ([beat digests](../watch/beat/2026-11-02.md)) — a snapshot cannot say which instance a client lands on.

### NEAR AI (gateway / E2EE / direct)

- **Gateway, plain (`near-ai-gateway-plain`):** plaintext held by gateway and selected worker. Our adapter checks each requested model against its own on-chain anchor entry at a recorded Base block — explicitly "operator policy, not … request-path proof" ([routes.json](../data/routes.json)). The May 2026 audit found the gateway never checks extracted compose hashes ([revisit 2026-05-02](https://github.com/amiller/devproof-audits-guide/blob/main/case-studies/near-ai-private-inference/DEVPROOF-REPORT-revisit-2026-05-02.md)), and no commit or release mentioning compose-hash enforcement appears in [cloud-api](https://github.com/nearai/cloud-api) 2026-10-01 → 2026-11-04: whoever holds the gateway's admin write chooses the backend that reads the prompt. A client-side check caught a live silent model substitution on 2026-05-05.
- **E2EE (`near-ai-gateway-e2ee`):** protected fields decrypt only in the model TEE; the gateway still reads unencrypted metadata/fields, and tool fields need `X-Encrypt-All-Fields` ([E2EE guide](https://docs.near.ai/cloud/guides/e2ee-chat-completions), fetched 2026-11-04). The guide instructs pinning the attested signing key — not compose hashes or the on-chain anchor. Reply confidentiality is separately broken: [#1061](https://github.com/nearai/cloud-api/issues/1061) lets an intermediary substitute the unauthenticated response-key header and read the reply; E2EE v3 ([#1296](https://github.com/nearai/cloud-api/pull/1296), merged 2026-10-28, deployed from [prod-20261029](https://github.com/nearai/cloud-api/releases)) forwards the reply key independently but does not authenticate it. Key routing is fragile: [PR #1313](https://github.com/nearai/cloud-api/pull/1313) (2026-10-29, unmerged) documents 36 prod + 21 staging `400 Decryption failed` errors when Qwen3.8-27B ran with two signing keys across backends.
- **Closed-chain client:** [hermes-agent #12201](https://github.com/NousResearch/hermes-agent/pull/12201) (2026-05) pins model → app_id, compose_hash, os_image_hash, kms_pubkey plus compose-manager action closure; under that client the README rated NEAR "✅ Stage 1" (2026-05-05 → 2026-08-18). Our adapter does not implement the full chain ([issue #29](https://github.com/amiller/awesome-private-inference/issues/29)).
- **Direct (`near-ai-direct`):** experimental; per-instance attestation, signatures may 404, "not recommended for … production verification workflows" ([docs](https://docs.near.ai/cloud/experimental/direct-completions), fetched 2026-11-04). Our lightclient never completed an encrypted request — no verdict.
- **Context:** [Epic #953](https://github.com/nearai/cloud-api/issues/953) decommissions the confidential-data infrastructure: DB off the CVM completed 2026-11-03, Private Chat shutdown deadline 2026-11-15; the E2EE guide was still live 2026-11-04. [nearai-cloud-verifier](https://github.com/nearai/nearai-cloud-verifier) has no commits since 2026-08-10 and no releases — its "default" cannot be pinned to a release artifact.

### Phala/RedPill

- **Substrate:** dstack is what NEAR's TEEs also run on. Hardening shipped through 0.6.x (on-chain `os_image_hash` registration [v0.6.0, 2026-09-28](https://github.com/Dstack-TEE/dstack/releases); vm_config/os_image_hash mismatch fix v0.6.1; mandatory KMS image verification v0.6.3, 2026-11-02) — but the ACI gateway still runs `dstack-0.5.9` as of 2026-11-03. The [zkSecurity audit](https://reports.zksecurity.xyz/reports/phala-dstack) (published 2025-08-13) fixed 14 findings in v0.5.3; KMS internals were out of scope; no newer audit found. The beat references an Oct 8–12 dstack guest-agent incident (Phala post-mortem 2026-10-19); details not re-examined here.
- **ACI gateway (`tee.redpill.ai`, `inference.phala.com`):** live verification on 2026-08-13/18 passed quote, quote-bound keyset, measured compose (RTMR3), live TLS SPKI, and end-to-end receipts (all seven §9.3 checks); key-custody policy is skipped by the public CLI ([redpill.md](../providers/redpill.md)). Remaining Stage-0 findings: the legacy `/v1/attestation/report` attests any model string (demonstrated 2026-08-18); `public_logs: true` + debug logging can echo ≤240-char request fragments on error paths; active routes are admin-mutable outside the measured compose.
- **2026-11-03 rollout:** [gateway-prod-2026-11-03](https://github.com/Dstack-TEE/private-ai-gateway/releases) changed the compose (repo `22d08e24` → `77fac126`) and **removed `DSTACK_ROOT_PUBLIC_KEY`** from `allowed_envs` (the `authorized_keys` write remains in the measured pre-launch script — inert unless the env is supplied); `public_logs: true` is still present; rollout to all three replicas at 17:10 PST came without advance notice (a ≥3-day notice policy was adopted afterwards). Our latest committed observation ([snapshot 2026-11-03T20:06Z](../data/latest.json)) predates that rollout — its `api.redpill.ai` outcome `rejected` was recorded against the old compose and needs refreshing (our-side staleness).
- **api.redpill.ai:** same CVM and keyset, **not TEE-only** — demonstrated 2026-08-18 with a 200 on `anthropic/claude-opus-5` and `upstream.verified: result=failed, required=false`: a signed receipt over an unattested hop. RedPill's docs formalize this: routed models go to "ordinary providers like OpenAI — the third party can see the prompt", and the SDK "does not check whether the gateway runs a production or development dstack OS image" ([docs.redpill.ai](https://docs.redpill.ai/confidential-ai/how-it-works), undated, fetched 2026-11-04).
- **Adjacent:** [private-ai-verifier](https://github.com/Phala-Network/private-ai-verifier) is dormant since 2026-06-10 and still decodes NVIDIA/ITA JWTs with `verify_signature=False` (affects adapters using those helpers, not the gateway's native DCAP path). The third-party [teep #175](https://github.com/13rac1/teep/pull/175) ACI/1 gap document (open) lists six gaps no deployment can close without a spec change (reviewed 2026-11-03).

## 2. What the client must do for the guarantee to hold

**Tinfoil:** run the verifier — Sigstore identity + measurement agreement, the AMD chain (V3), TLS SPKI pin, HPKE/report_data consistency; a stock OpenAI-SDK call gets none of it (secondhand: [flyingpenguin, 2026-10-13](https://www.flyingpenguin.com/micah-lees-tinfoil-ai-privacy-post-skips-the-privacy)). **NEAR plain gateway:** nothing to check — treat as an ordinary API. **NEAR E2EE:** verify the report, reject empty `model_attestations[]`, pin the signing key; for backend/code identity add closed-chain anchor pinning (hermes-style), which the docs do not instruct; reply confidentiality has no client-side remedy today. **Phala/RedPill ACI:** verify quote + keyset + measured compose + TLS SPKI + receipts (`aci` CLI), use session pins and `provider.aci_verified` (opt-in, invisible before sending) on `api.redpill.ai`, add dstack boot-measurement verification — custody checking is unimplemented publicly.

## 3. Provider findings vs our unfinished checks

**Provider-side (demonstrated or shipped, dated):** NEAR reply-key substitution un-fixed (#1061, 2026-09-14 → 2026-11-04); NEAR gateway accepts any TCB-current TDX backend absent client pinning (no enforcement found as of 2026-11-04); RedPill/Phala legacy attestation endpoint, debug logging and admin-mutable routing unchanged in the 2026-11-03 compose; api.redpill.ai non-TEE routing now documented by RedPill itself; private-ai-verifier JWT decoding unfixed; Tinfoil config moved off public repos (2026-07-16), safeguards classifier reads plaintext in an attested enclave (2026-09-15), no per-request GPU attestation.

**Our-side (unfinished, not provider findings):** Tinfoil AMD signature chain ([#26](https://github.com/amiller/awesome-private-inference/issues/26)) — now auditable against Tinfoil's V3 verifier code; our adapter reads legacy v1/v2 documents, not V3; no live encrypted Tinfoil request observed; NEAR compose-manager/request closure unverified and #1061 not reproduced live; ACI boot measurements and request path for the TEE-only hostnames still `not_checked`, and the `api.redpill.ai` rejection predates the 2026-11-03 compose. The [October review](../research/review-2026-10-13/review.md) says it directly: "A missing AMD signature check in our Python adapter is work for this repository, not evidence that the provider lacks hardware attestation."

## 4. Is either claim defensible?

**"Only Tinfoil is good" — strongest version:** Tinfoil is the only provider whose audited deployment had zero operator-controllable slots on the prompt path (2026-04-26), whose code identity is reproducibly pinned (Sigstore, dm-verity weights), and whose SDK verifies by default (TLS pinning since 2026-11-02) — and it has since shipped the strongest missing pieces (AMD chain, nonce, freshness witnesses in V3). **Where it is wrong:** "good" is not "verified today" — the AMD chain was never independently checked here, the operator-input trace predates the config move, two enclaves were never audited; it ignores that NEAR with a closed-chain client carried the same Stage 1 (2026-05-05 → 2026-08-18) on stronger anchoring (on-chain, independently checkable) than Tinfoil offers; and it treats "Phala" as one thing.

**"Phala and NEAR are also state of the art" — strongest version:** as *architecture*, yes — dstack is the most-audited substrate here (zkSecurity 2025, fixes shipped) and ACI is the most complete protocol shape here (receipts, keysets, measured compose, session pins); NEAR uniquely puts authorization on-chain where an independent client can check it; both serve TDX quotes with current TCB in our observations. **Where it is wrong:** state of the art must describe the deployed service and the default client. RedPill/Phala's deployment keeps its Stage-0 findings, runs dstack-0.5.9 while 0.6.x exists, and its public client skips custody; `api.redpill.ai` routes plaintext to third parties by default policy. NEAR's docs steer clients to signing-key pinning only, the reply-substitution issue is un-fixed 51 days after filing, and NEAR is retiring the confidential-data infrastructure behind Private Chat (deadline 2026-11-15). This mismatch is why brand-level stage awards were retired on 2026-10-13/14 ([review](../research/review-2026-10-13/review.md): "replace provider-wide Stage labels … with route-specific statements"); [stages.html](https://amiller.github.io/awesome-private-inference/stages.html) is now "Proposal draft-1 · no stages awarded".

## 5. What the comparison page must show for a reader to answer this themselves

1. **A per-path plaintext-holder table** (gateway / E2EE / direct × provider) naming every component that sees protected fields, bound to dated evidence — never a provider-level verdict.
2. **An explicit split of provider findings from our unfinished checks**, each with its demonstrating date/link or issue link, so "unknown" never reads as either "bad" or "fine".
3. **What the client must run, per path**, linked to a reference implementation, with the negative controls (substituted reply key, wrong model, stale quote, unapproved update) that have actually been executed against it.
4. **Audit scope and staleness:** which deployment/version each load-bearing audit examined, whether the traced code is still the served code, and what changed since (e.g., Tinfoil's 2026-07-16 config move; the 2026-11-03 ACI compose change).
5. **A "what would change this answer" column:** the specific provider-side fix and registry-side proof that would move each cell — e.g., a merged #1061 fix, our AMD-chain check closing #26, an implemented ACI custody policy.
