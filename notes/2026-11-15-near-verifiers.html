Problems that recur across these clients

  • Event-log values trusted without hashing. The dstack event log has a digest and a payload per entry. Replaying digests to RTMR3 proves nothing about the payload unless the digest is recomputed from it. private-ai-gateway's TS client (clients/verifier-ts/src/report.ts:173-182), abalone and BitRouter read app-id and compose-hash from payloads they never hashed, so a report server can keep genuine digests and substitute the values. The Rust aci-verify crate and the Gateway's staging build do it right.
  • The compose doesn't contain the serving code. NEAR's compose-manager pulls the proxy and model containers after boot from git tags in nearai/cvm-compose-files, with no minimum tag age. Pinning the compose hash pins the manager, not what reads the prompt.
  • One key, several deployments. On 2026-11-15, glm-5.3-flash ran on 3 instances with 3 different composes and one shared signing key. A receipt signed by that key doesn't say which one served the request.
  • E2EE v3 is the only version that binds the reply key (nearai inference-proxy #321). teep sends v2; abalone and hermes send v1; nobody sends v3.
  • Fail-open defaults. Warn-and-send on TCB, skipping the NVIDIA check when its key list is unreachable, and sending without E2EE after a failed check all leave the prompt going to an unverified machine.

Where the Near AI Gateway overlaps, and where it adds something

The quote, nonce and per-model key binding repeat what teep and aci-verify already do. The goal is different: the Gateway labels traces with their provenance after the fact, while teep protects the prompt before it is sent. The per-response receipt checked against an attested model key is something none of the other clients do. teep doesn't check NEAR reply signatures at all.

Suggestions, in order of how much they change:

  • Ship the staging checks. Without the pins and the event-log replay, any genuine TDX machine's key counts as a NEAR model key.
  • Reject receipts that don't name a model, and don't fall back to the requested model name when looking up the key set.
  • If Gateway users expect their prompts to be private, send the NEAR lane with E2EE to the attested model key, ideally v3, or through teep. Today the prompt goes to NEAR's API over plain HTTPS.
  • For the Rust verifier, aci-verify already has the dstack replay and could be shared rather than maintained twice.
