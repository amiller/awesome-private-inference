NEAR AI verifiers compared

A NEAR model machine boots a measured compose that runs only compose-manager, NEAR's update service. compose-manager then deploys the serving code from git commits in nearai/cvm-compose-files. So checking the model machine's quote tells you the update service is genuine, not what reads your prompt. A client has to follow the chain below to the end.

Read from source at pinned commits on 2026-11-15. Live runs are noted where they happened.

The chain a NEAR client has to check

  1. Model quote. The model machine's TDX quote verifies, TCB is current, debug is off, the NVIDIA GPU evidence verifies, and our nonce is in it.
  2. Measured compose. The compose hash in the quote is pinned, or authorized on-chain in NEAR's app contract on Base.
  3. Deployment log. compose-manager's own quote verifies, comes from the same machine, and its report data is sha256(log) || our nonce with the hash recomputed from the log.
  4. Deployed files. Every file still running is public at its commit, and a public archive has seen it for some minimum time.
  5. Send. The prompt is encrypted to the attested model key, and nothing is sent if any step fails.

Steps 3 and 4 work today, with two limits

We added steps 3 and 4 to the awesome-private-inference monitor on 2026-11-15 (verifiers/near_deployments.py). On live glm-5.3-flash and Qwen3.8-27B, every check passed except the age check, because the archive started that day. The monitor's first run recorded 43 deployed files, and each one's bytes matched its public commit. Some came from personal branches and experiments/ files, not release tags; one was tagged pranavraja99/glm53-pd-qualification.

  • The deployment log's quote can be produced by other containers. dstack's GetQuote signs any 64 bytes the caller supplies, and since dstack 0.6.0 apps can't extend RTMR3. In NEAR's pack-small-models.yaml, the inference proxies and a third-party levantolabs/sage2-hopper-pod container can call GetQuote. Once a container is deployed, it could serve a quote over a different log. The anchor it can't forge is the public commit history, which is why step 4 matters. A fix on NEAR's side would put each deployment into a register apps can't write.
  • Environment values aren't logged. compose-manager substitutes them into the file but leaves them out of the log, so a public file can still point somewhere unlogged.

Problems that recur across these clients

  • Event-log values trusted without hashing. Replaying digests to RTMR3 proves nothing about a payload unless the digest is recomputed from it. private-ai-gateway's TS client (clients/verifier-ts/src/report.ts:173-182), abalone and BitRouter skip this. teep (internal/attestation/eventlog.go:57-68), the Rust aci-verify crate and the Gateway's staging build do it.
  • One key, several deployments. On 2026-11-15, glm-5.3-flash ran on 3 instances with 3 different composes and one shared signing key. A receipt signed by that key doesn't say which one served the request. Steps 3 and 4 don't depend on which one: each instance has to pass.
  • E2EE v3 is the only version that binds the reply key (nearai inference-proxy #321). teep sends v2; abalone and hermes send v1; nobody sends v3.
  • Fail-open defaults. Warn-and-send on TCB, skipping the NVIDIA check during an outage, and sending without E2EE after a failed check all send the prompt to an unverified machine.

Suggestions

  • teep: add steps 3 and 4 for NEAR (#166). The compose-manager attestation is already in the response teep parses. The answer to #166's open question: compose-manager doesn't extend RTMR3; it binds the log through a second quote (compose-manager/src/main.rs:1236-1243).
  • NEAR: log env values, measure each deployment into a register apps can't write, set a nonzero minimum tag age, and check the log in cloud-api.
  • NEAR AI Gateway: ship the staging checks, reject receipts that don't name a model, and send the NEAR lane with E2EE to the attested model key if users expect their prompts to stay private.
