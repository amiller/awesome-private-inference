Private inference verifiers

The clients that check TEE attestation for private inference, compared across seven providers. Each was read from source at a pinned commit on 2026-11-15; live runs are noted where they happened.

A verifying client has to establish four things before it sends a prompt. The hardware is genuine and current. The code that will read the prompt is known, and changes to it are public. The prompt is encrypted to a key that the attested code holds. And the request is refused if any of these fails. Every provider places the code that reads the prompt somewhere different, so the hard part differs by provider.

Where each provider's serving code is, and who checks it

Tinfoil

The router's attested config names each model's repo, and the router admits a model enclave only if it matches that repo's Sigstore release, with weights pinned by dm-verity. Every release is in Sigstore's public Rekor log, so changes are public. Gaps: the client attests the router, not the model enclave; clients adopt the latest release immediately; and the control plane can rewrite model: "auto" requests outside the measurement.

NEAR AI

The measured compose runs only compose-manager, NEAR's update service. compose-manager then deploys the serving code from commits in nearai/cvm-compose-files, and reports what it deployed in a log bound to its own quote. A client has to follow the chain to the end:

  1. Model quote verifies, current TCB, NVIDIA evidence, our nonce.
  2. The measured compose is pinned or authorized on-chain on Base.
  3. compose-manager's quote verifies, comes from the same machine, and its report data is sha256(log) || our nonce.
  4. Every running file is public at its commit and has been seen by an archive for some minimum time.
  5. The prompt is encrypted to the attested model key, and nothing is sent if a step fails.

teep does 1, 2 and 5. Our monitor added 3 and 4 on 2026-11-15 (verifiers/near_deployments.py). On live glm-5.3-flash and Qwen3.8-27B every check passed except age; the archive started that day with 43 files, all matching their public commits. Some were deployed from personal branches and experiments/ files, not release tags.

Two limits remain on NEAR's side. dstack's GetQuote signs any report data the caller supplies, and since dstack 0.6.0 apps can't extend RTMR3. NEAR's compose gives GetQuote to the inference proxies and a third-party levantolabs/sage2-hopper-pod container, so a deployed container could serve a quote over a different log; the public commit history is the anchor it can't forge. And compose-manager doesn't log the environment values it substitutes into each file.

Phala Cloud and other ACI services

The client attests the ACI gateway and can pin the sessions the gateway holds with upstream workloads. Nobody applies a policy to those upstream workloads today (teep reports "workload policy not checked"), and the receipt naming the serving session arrives after the stream is delivered. Behind the gateway, "the operator" can be several companies.

Chutes

The serving code is excluded from the measurement (cfsv_wrapper.py:54), so no client policy over the quote can cover it.

Venice and NanoGPT

Venice's newer ACI/1 route exposes only the gateway; there has been no GPU evidence since 2026-11-12. Its legacy dstack route still gives per-host evidence, and teep blocks on it. NanoGPT's dstack route sends the prompt to NanoGPT unless E2EE is turned on.

Problems that recur across clients

  • Event-log values trusted without hashing. Replaying digests to RTMR3 proves nothing about a payload unless the digest is recomputed from it. private-ai-gateway's TS client (clients/verifier-ts/src/report.ts:173-182), abalone and BitRouter's removed verifier skip this. teep (internal/attestation/eventlog.go:57-68), the Rust aci-verify crate and the NEAR AI Gateway's staging build do it.
  • Releases adopted on sight. teep and tinfoil-go take the latest Tinfoil release, Privatemode's proxy takes any CDN manifest, and nobody waits before accepting a NEAR deployment. A public log gives visibility; a waiting period is what gives an observer time to object.
  • Reply authenticity. Only ACI receipts on Phala Cloud are verified (teep, pap), and only after delivery. NEAR's E2EE v3 binds the reply key (inference-proxy #321), but no client sends v3.
  • Fail-open defaults. Warn-and-send on TCB, skipping NVIDIA checks during an outage, sending without E2EE after a failed check, and gateways that forward unless a request is marked "required".

Suggestions

  • teep: add steps 3 and 4 for NEAR (#166). The answer to #166's open question: compose-manager doesn't extend RTMR3; it binds the log through a second quote (compose-manager/src/main.rs:1236-1243). Consider a waiting period before adopting a new Tinfoil release.
  • private-ai-gateway: recompute event digests in the TS client, and carry Tinfoil's Tinfoil-Enclave response header into the receipt.
  • NEAR: log environment values, measure each deployment into a register apps can't write, set a nonzero minimum tag age, and check the log in cloud-api.
  • NEAR AI Gateway: ship the staging checks, and send prompts with E2EE to the attested model key if users expect them to stay private.
