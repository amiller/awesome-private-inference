# Maple private inference: preliminary devproof audit (2026-10-13)

Status: **source and publication review, not a live or full audit**. Source inspected at Maple commit [`059b6b9ccb39fccd8cc65b1386affc8edfd37b61`](https://github.com/MaplePrivacyLabs/Maple/tree/059b6b9ccb39fccd8cc65b1386affc8edfd37b61), committed 2026-10-13 18:22 UTC. No account, paid request, client installation, enclave rebuild, independent Nitro signature verification, or provider-backend attestation was performed. The only network comparison was a read-only fetch of the four published PCR files at the canonical and legacy raw GitHub URLs; they matched byte for byte at observation time. A later `master` may differ.

## Claim and architecture

[Maple's proof page](https://www.trymaple.ai/proof) says a client verifies a fresh AWS Nitro attestation, checks approved PCR0, and creates an encrypted session; Maple's enclave then checks the model enclave before forwarding. The page explicitly says the browser check is served by Maple, the model enclave is not directly attested by the client, and a fingerprint match means Maple approved software, **not** that it came from public source. It also says Maple has not yet had an audit. These are advertised claims, not findings of this review.

The source shows at least three client surfaces, all leading to the OpenSecret Nitro service: web Research via the TypeScript SDK; installed desktop/mobile Research via the same frontend/SDK plus native packaging; and OpenAI-compatible callers via a local Maple Proxy, or a direct SDK integration. The [proxy documentation](https://www.trymaple.ai/docs/proxy) states tool-to-proxy traffic is plaintext and should stay on loopback. In the [proxy source](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/proxy/src/proxy.rs), startup performs an OpenSecret attestation handshake before protected forwarding. The [backend attestation routes](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/src/web/attestation_routes.rs) request a Nitro document with the caller's nonce and an ephemeral enclave public key, then consume the corresponding ephemeral secret at key exchange. The [TypeScript SDK](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/sdk/src/lib/getAttestation.ts) checks the attestation, PCR0, and public key before decrypting the session key; the [attestation parser](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/sdk/src/lib/attestation.ts) checks nonce, AWS root chain, document signature, and certificate validity. This is source-inspected behavior; it does not prove the shipped web bundle, native binary, proxy binary, or live enclave runs that code.

Plaintext observers differ by path. The user's own browser/app or local proxy sees the prompt before encryption; a compromised browser delivery path can replace client code. Maple's Nitro process sees decrypted content for routing and persistence logic. The [provider registry](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/src/provider_registry.rs) identifies **two separate inference stacks**, Tinfoil and Continuum/PrivateMode, with model-specific and weighted routes: `glm-5.3` may go to either, `glm-5.3-flash` only to Continuum, and several other models only to Tinfoil. Count these as separate provider trust paths, not a single Maple backend score. The OpenSecret process sends prompt plaintext toward the selected provider. Its [Tinfoil client](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/src/provider_client.rs) uses the Tinfoil Rust SDK's discovery/attestation and TLS pinning, with failure treated as unavailable. Its Continuum path is ordinary HTTP to a loopback sidecar; the [measured entrypoint](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/entrypoint.sh) launches `continuum-proxy` on `127.0.0.1:8092`, and the [EIF rootfs](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/flake.nix) includes that checked-in ARM64 binary. Thus OpenSecret-to-sidecar plaintext stays inside the Nitro image if the deployed image matches the source build, but the sidecar's onward PrivateMode attestation/policy has not been inspected. The rootfs measurement covers the binary bytes, not an established source-to-binary provenance chain. Network placement, host forwarders, actual route and backend worker identity remain unverified. A Maple PCR0 match alone cannot certify either upstream worker or the model weights.

## Reference-value consistency and authority

At the pinned source commit, [`pcrProd.json`](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/pcrProd.json) records current production PCR0 `21d27bd19cdd…be16b7a9`. It appears in the 158-entry [production history](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/pcrProdHistory.json) at entry 157, and in the approved lists of the [TypeScript SDK](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/sdk/src/lib/pcr.ts), [Rust SDK](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/sdk/rust/src/pcr.rs), and [Research client config](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/apps/maple-research/frontend/src/config/openSecretClientConfig.ts). All three also retain `643b3c293a4e…25e7943b66` as an explicit 2026-10-09 rollback root. These comparisons are **source consistency**, not live attestation. On 2026-10-13, canonical and legacy published `pcrProd.json`, `pcrProdHistory.json`, `pcrDev.json`, and `pcrDevHistory.json` matched byte for byte. Production history SHA-256 was `2b20459c263a5fb2b678d275925cadf484d933712ab98856d46450d8a2b07a24`; this is a point observation, not a continuity guarantee.

The SDKs use a built-in P-384 verification key and fetch the appropriate signed history from mutable `master` URLs after local root miss. Older installed clients use the [legacy OpenSecretCloud mirror](https://raw.githubusercontent.com/OpenSecretCloud/opensecret/master/pcrProdHistory.json), while current clients use the [Maple canonical history](https://raw.githubusercontent.com/MaplePrivacyLabs/Maple/master/services/opensecret/pcrProdHistory.json); the [compatibility procedure](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/docs/pcr-compatibility.md) explicitly requires both. The signature authenticates **lowercase PCR0 text only**. PCR1, PCR2, timestamp, environment label, order, source commit, build artifact, release version, and retirement status are not signed; the TypeScript verifier checks only PCR0 on a matching history row. Consequently, signatures establish approval by Maple's signing key, not reproducible build provenance or an auditable release sequence. Local embedded roots bypass history retrieval, including any future published retirement. Histories are designed to preserve prior entries and permit rollback; neither client enforces a maximum version or detects equivocation between histories, mirrors, CDN views, or client releases. An attacker with signing authority, or a mistaken signing operation, can admit an arbitrary image; a valid old image can remain acceptable indefinitely. This is an authority and rollback concern, not a demonstrated attack on today's service.

The [release runbook](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/docs/nitro-deploy.md) and [compatibility procedure](https://github.com/MaplePrivacyLabs/Maple/blob/059b6b9ccb39fccd8cc65b1386affc8edfd37b61/services/opensecret/docs/pcr-compatibility.md) describe reviewer-gated EIF building, signing, and matching both history locations. That is an operator process in source; this review did not verify release-builder output, an independent rebuild, signer custody, deployment artifact hash, KMS/IAM policy, or live PCR. The Nix rootfs includes OpenSecret, launch scripts, kernel, and the Continuum sidecar, but runtime provider URLs, credentials, route health and selection, secrets-manager contents, host vsock destinations, deployment parameters, and model weights/serving code are outside what the client PCR0 check alone proves. Check actual KMS conditions and all runtime inputs before asserting Maple operators cannot change the plaintext path.

## Concrete onboarding and monitoring gate

1. Inventory **each** shipped client (web URL/bundle, desktop/mobile release hashes, proxy image/binary, direct SDK versions) and each public model-to-provider route at an immutable Maple source commit. Record actual backend/sidecar endpoints and identify who may change them. A model with two providers needs two upstream audit rows.
2. For a fresh client nonce, capture a **sanitized** Nitro document and independently verify AWS chain/signature, nonce, certificate time, nonzero ephemeral public key, key-exchange continuity, and PCR0 against a locally reviewed policy. Test altered nonce, key, PCR0, expired cert, and history fetch failure; all must prevent prompt transmission. Do this on the actual web, native and proxy request paths, not only the proof page.
3. Rebuild the EIF from the immutable source on a suitable remote builder and compare PCR0/1/2 and artifact digest to the release manifest and live quote. As a proposed publication improvement, bind a signed release statement to source commit, builder, artifact digest, *all* measured PCRs, environment, validity window, predecessor and operator approval. The current PCR0-only signatures cannot satisfy that proposed gate; report this limitation rather than treating the statement as already available. Review the checked-in Continuum sidecar's upstream source/build mapping separately.
4. For each model and selected route, capture upstream attestation evidence before forwarding a canary request. Verify Tinfoil's discovered router/worker, TLS pin and model identity; verify Continuum/PrivateMode sidecar and worker chain, including whether its onward request is encrypted to an attested key. Show a failure-injection test in which a bad upstream quote or route substitution blocks forwarding. Record prompt-plaintext observers at every hop, including web delivery and local proxy callers. Do not treat OpenSecret's successful quote as proof of the chosen upstream.
5. Publish per-route observations to a signed, append-only continuity record: client version, Maple PCR0/1/2, release/source digest, provider, worker identity/measurement, model ID, attested key, timestamp, and vantage. Compare canonical and legacy histories and at least two independent fetches daily. Alert on new or regressed PCR, unexpected old-root use, missing mirror entry, changed provider/worker/model, unsigned or unseen reference value, and split views. Keep the raw signed evidence privately if it could contain secrets; publish hashes and redacted reports.

**Acceptance for a first scored row:** fresh live Nitro verification and same-session key binding pass; independently rebuilt measured image matches a signed release statement; actual request routing and both possible upstream attestations are demonstrated; every prompt-plaintext process is measured and tied to that statement or explicitly marked outside the trust boundary; invalid/missing quote, stale root, altered model, and mirror disagreement fail closed before prompt forwarding. Until then, score Maple's client-to-Nitro verification as *source-inspected*, and mark deployed image provenance and upstream confidentiality **unverified**. Do not combine Tinfoil and Continuum into one passing cell.

## Evidence limits

This review fetched public source and history only. No live attestation response, credentials, paid inference request, release binary, EIF build, provider-side quote, or independent signing-key check was obtained. The point-in-time publication comparison establishes file equality, not valid signatures or correct deployment. The source changes rapidly, so future work should pin the exact client release and deployed backend SHA, not `master`.
