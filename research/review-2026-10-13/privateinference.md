# Private Inference (`privateinference.gg`) — preliminary devproof review

**Observed 2026-10-13 America/Detroit (2026-10-14 00:57–00:59 UTC).** This is a desk/source and unauthenticated-endpoint review, **not** a full audit or a successful private inference proof. The service is invite-only; no API key, paid call, quote, receipt, or packet trace was available. Its published [How it works](https://privateinference.gg/how-it-works) is unusually explicit about the current boundary and two known gaps. The `v0.2.0` [changelog](https://privateinference.gg/changelog) dates the private-execution beta to 2026-09-26.

## Claim and actual trust boundary

The site advertises ordinary OpenAI-compatible routing, zero-data-retention (ZDR) routing, and a distinct **private execution (beta)** tier using NEAR AI Cloud. On standard and ZDR routes, Private Inference says its proxy sees plaintext prompts while relaying them; ZDR is a retention policy, not client-to-model encryption. The site says only NEAR-operated TEE models are admitted to the private tier and no lower-tier fallback occurs. These are **provider claims**, not properties verified by this review. See [How it works, Suppliers and Private execution](https://privateinference.gg/how-it-works).

```text
standard / ZDR:
user --TLS, plaintext at PI--> PI proxy --provider route--> 0G / CheaperInference / OpenRouter
                         ^ PI can read prompt and response; supplier can read them

private beta (claimed):
browser --verify NEAR model quote, encrypt fields to quoted Ed25519 key-->
PI proxy --ciphertext, API/payment metadata--> NEAR gateway --ciphertext--> model TEE
browser <--encrypted reply / clear usage metadata-- PI <--encrypted reply-- model TEE
                         ^ PI and NEAR gateway see model, timing, sizes, token counts,
                           max_tokens, API identity/IP; model TEE sees plaintext
```

The private path's `X-Client-Pub-Key` response-key header is not authenticated inside the encrypted request. A relay able to replace it can obtain the real response plaintext even when the prompt remains encrypted; client receipt verification detects a changed exchange afterward, but cannot prevent disclosure. Both [PI's beta caveat](https://privateinference.gg/how-it-works) and the still-open [NEAR cloud-api issue #1061](https://github.com/nearai/cloud-api/issues/1061) describe this exact attack. Thus “PI never sees the reply” is conditional on a non-malicious relay until the protocol binds the response key.

## Reference-value consistency: the decisive gap

A hardware-valid quote proves that **some** workload with the reported measurement and key ran in a TEE. The bundle checks that `sha256(app_compose)` is committed in `MRCONFIGID` and that an event log replays to RTMR3. It does **not** establish that the compose, OS image, serving code, weights, runtime configuration, or model identity are approved for this product. PI expressly says its app compose and OS image are “measured and shown, not compared with a published baseline” in [How it works](https://privateinference.gg/how-it-works). This is a sound self-consistency check but not a developer-approved reference-value check. The repo's [NEAR provider study](../../providers/near-ai.md) and [observation-log design](../observation-log.md) show the stricter baseline/continuity approach, but those checks are not evidence that PI runs them.

| Question | Current finding | Required closure |
|---|---|---|
| Who publishes the accepted value? | No PI-approved, signed `model → app_id/compose/OS/weights` manifest was found or consumed by the inspected browser bundle. NEAR publishes [deployment manifests](https://github.com/nearai/cvm-compose-files), but publication alone is not client authorization. | Identify an independent, authenticated policy authority and expose its exact version/digest to clients. |
| Can a reviewer reproduce it? | Bundle hash is capturable, but no source commit/build provenance was established for PI's served JS. A compose hash can be recomputed from a returned string; the actual container/image and model-weight preimages were not linked through a verified reproducible build here. | Pin source commits, build inputs and output digests; independently rebuild or verify signed provenance; tie model weights/revision and serving code to measured preimages. |
| Who may update it? | PI private browser path accepts a newly self-consistent attestation without a policy approval step. NEAR's own governance/on-chain authorization is a separate possible authority, not checked by this bundle. | Require signed, reviewed updates with owner/threshold policy; check on-chain authorization or static pins independent of the attestation endpoint. |
| Can rollback or equivocation be seen? | Five-minute per-model cache and re-verification on key change address freshness locally, not historical continuity. No monotonic version, minimum accepted epoch, cross-client log, or witnessed checkpoint is visible in the bundle. | Record each model/key/compose/OS transition, reject unapproved rollback, and publish witnessed observations or an append-only log so split views can be compared. |
| What is outside measurement? | PI says app compose and OS are displayed but unapproved; runtime env/secret values, model artifacts, service routes, and logging/telemetry were not shown to be measured or policy-pinned. | Audit which config fields are actually measured, including image digests, command, mounts, env, secrets, debug/SSH access, model weights, and outbound network paths; report explicit exclusions. |

The source-inspected model-name comparison deserves a targeted negative test: return a quote for model B in an otherwise valid response to a request for model A and check that the browser refuses **before** encryption. The live PI server may prohibit such substitution already; this review cannot establish that from the bundle alone. Independent policy must bind both the **requested model** and the **approved workload** to the attested key. A key match alone is insufficient: this repo has observed a legitimate NEAR compose rotation on the same signing address (see [NEAR provider history](../../providers/near-ai.md)).

## Concrete onboarding workflow and pass criteria

1. **Define tier and plaintext boundary.** Represent `standard`, `zdr`, and `private` as distinct products in any scorecard. Require an explicit `private` model catalog entry and fail closed if routing selects a supplier other than NEAR. Test that standard/ZDR requests are never scored as TEE-private.
2. **Capture a credentialed, fresh live bundle without sensitive prompts.** Save raw attestation, quote, event log, GPU evidence, request nonce, response status, model id, timestamp, and exact served browser-bundle digest. Independently verify Intel and NVIDIA signatures/verdicts, quote TCB/debug state, nonce, report-data ↔ signing/encryption key, RTMR3 replay, and `MRCONFIGID` ↔ compose. Accept only if every eligible serving instance passes. The current 401 blocks this step.
3. **Close the reference chain.** For each private model, select an independently approved `(model id, app id, compose hash, OS image hash, code/image digest, model artifact revision, KMS identity)` policy. Verify from NEAR's public [compose files](https://github.com/nearai/cvm-compose-files) and its authorization record, or maintain a reviewed static pin; record who signed/approved each update. Fail a quote whose self-consistent value is absent from the approved set, including a valid quote with a different `model_name`.
4. **Prove the request path.** With a funded test key, encrypt a harmless canary to the verified key, capture ciphertext leaving the client; establish PI forwarding behavior through controlled server instrumentation if available, otherwise leave that behavior unresolved; validate the model's response signature over exact request/reply bytes and usage, and force a key rotation. Include a malicious-proxy test that swaps `X-Client-Pub-Key`; private *response* confidentiality should remain **failed** until [cloud-api #1061](https://github.com/nearai/cloud-api/issues/1061) is fixed and deployed.
5. **Verify policy failure modes.** Exercise changed compose, changed OS, stale quote, wrong nonce, invalid GPU verdict, wrong model name, missing instance evidence, and standard-route fallback. Each must reject before prompt disclosure. Record which checks are client-enforced versus merely server-asserted.

Onboarding succeeds only when a credentialed end-to-end trace proves hardware/key/session binding **and** an independently authorized, reproducible reference set covers every plaintext-reading workload. The current evidence supports a **candidate, unverified** private tier; it does not support a full devproof pass.

## Monitoring after onboarding

At each observation, sample all private models from more than one network vantage with fresh nonces and log raw evidence hashes, exact model name, key, compose/OS hashes, app id, GPU/TCB status, browser build digest, and policy-manifest version. Diff against the last accepted observation **and** the independently approved set. Alert on unapproved additions, old-version rollback, same-key compose changes, differing simultaneous views, unexpected supplier/fallback, stale evidence, and a widened measured/unmeasured config boundary. Publish an append-only, signed checkpoint and a complaint feed as proposed in this repo's [observation log](../observation-log.md). Recheck the response-key protocol fix, route behavior, and browser bundle on each release; a successful quote from one day is not a standing authorization.
