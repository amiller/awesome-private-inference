# Confidential inference landscape and two scoped audits — 2026-10-13

This is a discovery and triage record, not a provider verdict or an exhaustive market census. It complements the existing NEAR, Tinfoil, Chutes, RedPill/Phala, and Venice work. The two audits below are **public-document/code review plus small unauthenticated endpoint probes**. Hardware signatures, source-to-image reproduction, an encrypted completion, and request-bound routing were **not** verified. In particular, a JSON nonce echo is not proof of hardware nonce binding.

The selection criterion is audit value: an independently operated inference route, a public verifier and reference-value story, a reachable evidence surface, and a materially different trust topology. A second brand using the same upstream should be recorded as a route, not counted as a second independent inference stack. The inventory is a set of leads found through targeted web searches on this date, not a denominator for any coverage percentage.

These categories prevent three conflations: a consumer application with an attested backend is not automatically a reusable inference API; an attested routing proxy is not the inference worker; TLS, data-retention policy, or locally run models provide different privacy properties from remote attested inference. Discovery of a name alone is not evidence of a working confidential route.

## Scoped audit 1: Privatemode

**Boundary and route.** The [architecture](https://docs.privatemode.ai/security/attestation/overview/) says a client proxy/SDK verifies a Contrast Coordinator and its manifest. The Coordinator verifies a secret service and AI workers before issuing mesh certificates. The client establishes a hybrid HPKE key with the secret service; it distributes keys to admitted workers. The worker's inference proxy decrypts, sends plaintext locally to vLLM, then encrypts the response. [Encryption docs](https://docs.privatemode.ai/security/encryption/) identify `model`, token limits, streaming flags and `n` as unencrypted request metadata, with `id` and usage unencrypted on response. This is transitive verification, not a direct client-to-worker quote. The secret service can access prompt encryption keys by design.

**Reference-value inventory.** The [manifest specification](https://docs.privatemode.ai/security/attestation/manifest/) says `ReferenceValues` pin CPU launch measurement/TCB/platform/machine identities, while `Policies` contain hashes of runtime policies that pin container image digest, argv, environment and mounts. Worker policy also pins the `disk-mounter` argument holding a dm-verity model-weight root. [Evidence docs](https://docs.privatemode.ai/security/attestation/attestation-evidence/) describe SNP `MEASUREMENT` + `HOST_DATA` + `REPORT_DATA` or TDX `MRTD`/RTMRs + `MRCONFIGID` + `REPORTDATA`, session nonce and CA bindings, plus GPU SPDM/RIM checks inside the worker. The public [source repo](https://github.com/edgelesssys/privatemode-public) contains proxy, SDK, secret service, inference proxy, attestation agent, deployment description and build inputs. The [reproduction guide](https://docs.privatemode.ai/cookbook/verify-source/) lays out image/manifest reproduction; we did not run its heavy Nix/container/model builds.

**Observed, 2026-10-13.** An unauthenticated GET of `https://cdn.confidential.cloud/privatemode/v2/manifest.json` returned 5,992 bytes with SHA-256 `9f5ac6bf38431fb073c2185bd9b344140e776b4f7c32eee595716e9456bdec2a`, 8 policy entries, and one each of `snp` and `tdx` reference entries. Policy workload IDs identify a Coordinator, secret service, several model workers and an unstructured API. This proves publication and parseability of **one observed manifest version**, not that the service currently enforces it or that each policy is safe. The manifest is mutable at its URL; preserve exact bytes and timestamp for a real audit.

**Material review question.** The [proxy documentation](https://docs.privatemode.ai/api/proxy-configuration/) says default mode fetches Edgeless's latest manifest and, after a validation failure, retries with it, logging locally; `--manifest-path` pins an independently reviewed file. Thus default success means “matches the provider-published current expectation,” whereas a pinned setup can detect unauthorized changes. A local log is valuable for continuity only if persisted, examined and ideally shared; the default Docker command does not demonstrate that persistence. The proxy docs also say NVIDIA OCSP `unknown` is accepted by default and revoked certificates get a 48-hour grace period. Those are explicit policy choices to test rather than silently scoring GPU revocation as strict. [Trust documentation](https://docs.privatemode.ai/security/trust-and-compliance/) says its proxyless path verifies the backend on the user's behalf and does not currently support client-side attestation; it needs a separate route verdict.

**Next workflow and pass condition.** Pin a release commit and preserve manifest bytes/digest; reproduce the reference values on an appropriately sized remote builder, then inspect *all* policy entries for host inputs and egress. Use a pinned manifest with the SDK and local proxy, prove a good attestation/key exchange and encrypted completion, and mutate manifest, CPU measurement, workload policy, GPU verdict and mesh certificate in controlled tests to show fail-closed behavior before payload release. Trace secret-service-to-worker admission and key distribution in source; verify model-weight root against the exact served model revision. Test a second session after deployment change and distinguish local-log-only detection from client rejection. Score proxyless separately. A Stage-1 claim would require that the reviewed reference values cover every plaintext holder and that the tested client actually binds its encryption key and route to those values; this audit has not established that.

## Scoped audit 2: Confidential AI Inference

**Boundary and route.** The [public source](https://github.com/confidential-dot-ai/confidential-inference) describes a TDX ConfOS image, c8s policies, gateway, SGLang router/workers and a verifier. Its [threat model](https://github.com/confidential-dot-ai/confidential-inference/blob/main/docs/threat-model.md) says public TLS terminates inside a c8s `tls-lb` TEE, then plain HTTP crosses the protected cluster mesh to the gateway, router and workers. The [attestation guide](https://confidential.ai/docs/inference-api/attestation) describes a fresh nonce, measured image, sealed allowlist, front-door TLS binding, workload receipts, release digests and raw NVIDIA evidence. It explicitly says raw GPU evidence is not verified GPU proof absent a compatible verifier. [TEErminator](https://github.com/confidential-dot-ai/teerminator) documents checking a nonce-bound `attest-lb` bundle against the *same upstream TLS certificate* and pinning full TDX MRTD+RTMR1+RTMR2, workload and allowlist; its general README alone is not a live verdict for this deployment.

**Reference-value inventory.** The source repo identifies [signed release bundles and a verifier procedure](https://github.com/confidential-dot-ai/confidential-inference#verify-one-live-attestation), production node manifest, SGLang source lock, `https://api.confidential.ai/allowlist`, operator public key, mesh CA and c8s source lock. These are distinct trust inputs. The repo notes that live environment configuration and deployment receipts reside in a private operator repository. A faithful audit must reconstruct the exact signed release asset for the observed release, check its Sigstore identity, match exact allowlist bytes, quote and workload receipts, and bind the TLS session that carries the eventual prompt. Reading the allowlist or release name alone does not suffice.

**Observed, 2026-10-13.** An unauthenticated GET of `/health` returned HTTP 200 `{"status":"ok"}`. GET `/allowlist` returned 14,463 bytes with SHA-256 `eb60199e3664fc2480688a309e50c55e5eebb42f38aa5f20b98b519f998a0dcc`, schema `c8s.allowlist/v1`, and 15 named workloads. GET `/attestation?nonce=<fresh 32-byte base64url>` returned ~890 KB, `schemaVersion: 2`, the supplied nonce in its top-level `nonce`, six `receipts`, `frontDoor`, `tls`, `c8s`, `gpuEvidence`, and release ID `v0.13.28-rc.2`. A second nonce probe returned the same structural shape. These are reachability and parser checks only; no c8s, DCAP, Sigstore, GPU or TLS-channel verification was performed.

**Material review question.** The [source threat model](https://github.com/confidential-dot-ai/confidential-inference/blob/main/docs/threat-model.md) is unusually candid about two potential operator-control paths: its current static-policy operator key can still write CDS secrets and obtain a `system:masters` cluster-admin credential; the unencrypted control-plane state disk contains RKE2 server state, including a client CA key. The document reasons that cluster-admin access can exec into a pod inside the TEE and read workload memory, and marks operator-key removal and disk encryption as planned. These are **source-documented design gaps**, not an independently demonstrated live compromise. The same document says allowlisting image digest and argv does not cover all environment/mount/pod fields, and a successful `/attestation` proves admission rather than current routing or model use. Its GPU section describes a measured boot gate but also says the relying party receives only raw evidence; reconcile that implementation with the public guide before awarding a GPU verification check.

**Next workflow and pass condition.** Download the GitHub Release assets for observed `v0.13.28-rc.2` and match the signed release bundle, commit, node manifest and allowlist to the live response. Run the published verifier on a remote or light environment with no large build, then run TEErminator with *reviewed/pinned* image, workload, allowlist, TLS name, TCB and CA inputs and prove fail-closed behavior for altered values. Trace the actual completion through gateway/router/worker and collect request-bound evidence. For a Stage-1 confidentiality verdict, the operator credential and readable control-plane disk paths must be closed or cryptographically excluded from the actual production build; measured launch/admission evidence alone cannot exclude them. Require independent evidence that the served model and GPU are the reviewed ones, rather than treating a raw evidence field or `/health` as a pass.

## Reusable success gates for expansion

1. **Enumerate routes and plaintext holders.** Identify the selected client mode, gateway, key service, worker, model, GPU and any alternate proxyless/direct path. Record the endpoint actually used for a completion.
2. **Acquire exact, versioned expectations.** Preserve signed release/manifest/allowlist bytes with digest, origin, publication time and authorizing trust root. Record whether client policy pins, auto-adopts or merely logs a new value. Capture continuity changes as the [observation-log design](../observation-log.md) proposes, without treating first-seen as authorization.
3. **Verify each evidence link.** Validate hardware signature, TCB/debug state, freshness, workload configuration, model/weight identity, GPU state, key custody and the exact TLS/application key used. A provider's `verified:true` field is an input to investigate, not a result.
4. **Bind a real request.** Show that the attested recipient decrypted this request and that response/receipt/route claims refer to the same session. Test controlled mismatches and confirm the client refuses before plaintext leaves it.
5. **Separate scope and failure cause.** Score source claims, public endpoints, cryptographic checks and runtime request observations separately. Distinguish unavailable evidence from failed verification and product policy from hardware guarantee. Treat new providers as candidates until a complete route-specific audit exists.

The next two deep audits should be Privatemode and Confidential AI. Confer and Apple PCC supply valuable public-transparency comparators but should retain their consumer-service category. This prioritization is based on the evidence surfaces above, not a claim that the search found every provider.
