## Routes abalone supports

Three admitted providers (`PJ:2-80`): `nearai` (own NEAR verifier), `redpill` and `phala` (both ACI/1 through the same vendored client). Not supported, so not rated: Tinfoil or any SNP route (the ACI verifier implements TDX only, `R:201-207`), Chutes (refused, `N:172-174`; not in either `upstreams.admit`, `PJ:20-26,44-50`), Venice, NanoGPT, Privatemode (not found in `PJ`). `nearai-outside` is a deliberate unattested route that sends a user-approved payload with no verification (`lib/mediate.mjs:77-86`); it is out of scope here.

### Counterexample: compose and app id are not bound

On the recorded NEAR attestation (`tests/fixtures/near/attestation.json`), the script below copies the model attestation, replaces the `compose-hash` and `app-id` payloads and `app_compose` with the gateway's, and leaves every RTMR3 `digest` untouched. `checkReport` accepts it. It reports the gateway's compose `8bc802c9…` and app `0xf550fdfb…` for a CVM whose RTMR3 still measures compose `c82b1a2e…` under app `0x2c0a0c96…`. Only the JSON-RPC `id` in the Base replay was normalised; the eth_call itself is the recorded one.

```
model compose payload c82b1a2eaf699615 -> 8bc802c9c8043a9c | digest kept 7908c30c0a22b6ed
model app-id 2c0a0c96cb6dbd659bf1446e2f3fce58172ff91b -> f550fdfb4eb8ad787c1bcd423f091cbb4a4431ae
ACCEPTED. compose_hashes: [ '8bc802c9c8043a9c' ] apps: [ '0xf550fdfb4eb8ad787c1bcd423f091cbb4a4431ae' ]
```

Consequence: whoever serves or relays the report (NEAR, or a gift peer) can name any compose that some DstackApp allows. They can also name an app-id contract of their own that returns true [i]; that variant was not run. The on-chain admission check therefore constrains nothing about the code actually running. The hardware, nonce, TLS and model-key bindings are unaffected. The same `verifyComposeMeasurement` serves ACI id-4 (`T:375`), where the compose is not pinned anyway. The ACI production-OS check does compare the event `digest` with a pinned digest (`T:149-170`), so that one payload is bound. The gateway's Rust verifier recomputes the digest (part D, `crates/aci-verify/src/dstack.rs:160-170` at `e9b6ae8a`). The TS verifier abalone vendors does not, and it matches upstream `clients/verifier-ts` here, since `report.ts` differs from it only in the TCB gate and the PCS URL.

## 3. Delegation and convergence

abalone delegates nothing to teep, pap or a running private-ai-gateway. It reimplements both paths:

- **NEAR**: `lib/near.mjs` is a port of hermes' E2EE transport and `_nearai-verifier` (`N:1-2`). It inherits hermes' v1 E2EE (part B) and adds per-instance appraisal, GPU JWT signature checking, the on-chain compose lookup and the gift-route chat signature.
- **ACI**: `aci/verifier-ts` is a fork of the gateway's `clients/verifier-ts`. `aci/provider` and `aci/pi-provider-*` are not in the gateway repo at `e9b6ae8a`, and their origin was not found. All of `aci/` arrived in one commit (`git log -- aci`: `64769e9`). Against `e9b6ae8a`, abalone adds the UpToDate gate, Intel PCS in place of Phala PCCS and the OS allowlist (`R:10,218,238-240`; `T:72-123`). It lacks the newer `runtime/constraints.ts` and the multi-member identity in `runtime/connection.ts`.

Converging on teep + ACI would mean concretely:

- **NEAR → teep `nearcloud`.** Delete `verifyNearModel`/`checkReport`/`quote`/`gpu`/`measured`/`allowedOnChain`/`encrypt`/`decrypt` (`N:47-201,221-232`) and the crypto inside `fetchE2ee`/`decryptSse` (`NP:26-80,103-155`). Point the provider at a local teep proxy. What this gains, per part A row `nearcloud`: MRTD E, TCB E, E2EE v2 (still no reply-key binding; only v3 binds it). What must be kept or ported: tool stripping (`NP:110-116`), the gift transport and charge check, and `chatSignatureFails` (`N:203-219`), which neither teep row in part A has. The gift route has no teep equivalent. teep would have to run on the client with the peer as its upstream transport, and that has not been built.
- **ACI → upstream `@phala/aci-verifier` (or teep's ACI/1 path).** Replace `aci/verifier-ts` with the published package. Keep abalone's two policies as options or upstream them; the TCB gate and OS allowlist are not upstream. Turn on key custody (teep enforces it against a TOFU KMS root, part A `A:153-174`). Pin `acceptedSessionIds` per request, or call `receiptVerdict` (`U:26-30`) inside `auditResponse` so the serving upstream is checked against `upstreams.admit` every time. Move `vet` onto the pinned transport.
- **Either way**, two fixes are needed before compose, app id or OS image mean anything. Recompute each event digest from its payload; upstream TS has the same `replayRtmr3`, so swapping verifiers does not fix this. Then pin MRTD and RTMR0-2 (or the OS image they imply), because the guest OS writes RTMR3: an unpinned OS can emit NEAR's genuine digests [i].
