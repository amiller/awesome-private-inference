## Shape

There are two hops, and each has its own verifier.

1. **Buyer → "Market".** The Market is a dstack CVM on Phala. It runs the Rust host, which is built against the private `bitrouter-cloud` crates, plus Postgres, Redis, nginx and the Chutes Python bridge. Its keyset is ACI/1 (`H/attestation.rs:209-228`). The buyer verifies the Market with `@phala/aci-verifier`, which is private-ai-gateway's `clients/verifier-ts` (`AV/../package.json:6-9`), plus its own checks.
2. **Market → upstream.** A loopback bridge next to the Market host verifies the provider and encrypts to it:
   - Chutes: `CG`, inside the Market image (`deploy/phala/Dockerfile.chutes:24`).
   - NEAR: `NB`, which wraps NEAR's SDK. `NB` is not in any `deploy/` image. The runbook starts it by hand (`docs/inference-comparison.md:107-110`).

The buyer never sees the upstream evidence. `buy` prints `upstream_verified:false` (`MB/cli.mjs:48`), and the ACI client is told `requireVerified:false, requireReceipt:false` (`MB/connection.mjs:183`). `CG` sets `X-ACI-Upstream-Session` (`CG:364`). Nothing outside `CG` and its test reads it. Preflight records are published at `/market/v1/provider-evidence/` (`deploy/phala/packaged/market/nginx.conf:58-59`), but no client fetches them.

**Reuse:**
- `aci-protocol` from private-ai-gateway `0edde219` (`H/../Cargo.toml:25`).
- The E2EE v2 X25519 construction, copied from the same commit (`H/e2ee.rs:1-8`).
- `@phala/aci-verifier`.

Not found: teep, nearai-cloud-verifier, Chutes' own verifier, or bitrouter's deleted `bitrouter-attestation`. The Chutes verifier is new Python on `dcap-qvl==0.7.1` and `PyJWT` (`deploy/chutes/requirements-gateway.txt`).

## Receipts

The Market signs `{receipt, idempotency_key, request_id, purpose:"market.receipt.v1", workload_keyset_digest, key_id}` with an ed25519 key. The key is generated per boot and listed in the attested keyset (`H/attestation.rs:200-202,214-218`; `H/financial_receipt.rs:255-267`).

- **When it is signed.** The signature is made at GET time over a Postgres row, and only once settlement is committed (`:157-165`).
- **What `receipt` contains.** The inner `receipt` object is a row from `market_inference_receipts`, which the private `bitrouter-cloud` crate writes, so its schema is not reviewable here. The signer adds no request or response digest (`H/financial_receipt.rs:255-262`). The test helper `MB/test/signed-receipt.mjs` and the vectors in `MB/test/vectors/` (E2EE only) show no content digest either. The one `request_sha256` in `H/live.rs:618` is a seller-registration test fixture.
- **When it is checked.** The buyer checks the signature after delivery, in a separate command, and only against the current connection's keyset digest (`MB/receipt-verify.mjs:119-121`). The signature comes from whichever boot answers the GET, not necessarily the boot that ran the inference. A copy saved with `--out` can't be re-checked against a later boot's keyset.
- **What it attests.** It is a billing record, not an execution receipt. The docs say so (`docs/acceptance/2026-11-14-chutes-live.md:50-52,72-73`).

## Own docs vs code

- **The fix for the #701 bug class (RTMR3 replay over stored digests, so payloads can be swapped) is real, but only on one path.** `assertMeasuredEvents` recomputes `sha384(type‖":"‖event‖":"‖payload)`, then checks `app-id`/`compose-hash` before `system-ready` (`MB/connection.mjs:96-147`). Its comment and test name the bug in the pinned ACI library (`:97-98`, `MB/test/policy.test.mjs:52-75`). `verify-deployment.mjs` still lacks the fix, and that is what drives the "verified" badge in the market playground (`clients/market-playground/src/AttestationPanel.tsx:49,96`).
- **Tagline vs code.** The tagline is "Let agents buy inference they can verify" (README:3). The agent/MPP path verifies nothing. Only the operator CLI and the comparison runner (`services/inference-comparison/market-executor.mjs:79-122`) call `connectMarket`. The README itself says the existing records "do not establish one connected, funded agent loop" and that the GPU TEE path doesn't prove loaded weights or a per-request receipt.
- **Stale doc.** `docs/market-buyer-verification.md:20-21,29-30` predates two changes: purchase-field E2EE and `assertMeasuredEvents`. It says no E2EE is enabled and that RTMR3 compose checking is delegated to the ACI runtime. Prompt E2EE is still not enabled.
- **Spec vs code.** The hackathon spec prefers "an attestation-bound E2E encrypted channel, TLS terminated inside the confidential Market", and says attestation covers approved programs and config, not provider honesty (`docs/specs/2026-11-11-private-market-hackathon.md:127,135`, Chinese). The code matches that for the buyer→Market hop.
- **Chutes claims match the code.** `docs/acceptance/2026-11-14-chutes-live.md:33-36,47-52` describes Intel-root DCAP, UpToDate with no advisories, debug off, MRTD+RTMR0-3, nonce/ML-KEM binding and NRAS ES384. It also lists the gaps: vendor-published profiles, weights and topology unproven, preflight ≠ execution receipt. The doc calls itself a historical run of a pre-integration binary.
- **Measured image built partly from private source.** The Market image is pinned by digest in the compose (`scripts/prepare-packaged-phala.py:14-18,36-37`), and the Chutes seed, with its allowlist, is baked into it. But the host binary is built from private `bitrouter-cloud` (`deploy/phala/Dockerfile.chutes:7-11` needs a GitHub token). A buyer can pin the compose but cannot review what the measured image does with the plaintext prompt.
- **Unmeasured seed in the example template.** The older `deploy/phala/compose.chutes.example.yaml:4,14,24` reads the image digest and seed hash from `${…}` interpolation, and mounts the seed from `/dstack/persistent`. If those are sealed env values, the compose hash doesn't measure them [i]. The packaged path replaces this.
