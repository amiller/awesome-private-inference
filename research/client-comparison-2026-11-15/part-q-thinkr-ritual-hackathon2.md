## 1. Thinkr: a Tinfoil client, not its own enclave

The "private lane" is Tinfoil's router. The verifier README says "The provider of the enclave is Tinfoil. The verifier uses no code of Tinfoil" (`thinkr-verifier/README.md:8-10`); the default repo is `tinfoilsh/confidential-model-router` and the enclave `inference.tinfoil.sh` (`src/config/tinfoil.ts:8`, README `:28`, `:40`). The proxy fetches the bundle from `https://atc.tinfoil.sh/attestation` and passes it to the browser unchanged (`thinkr-proxy/src/tinfoil/attestation.ts:1-3`, `src/config/tinfoil.ts:6`). Thinkr wrote its own verifier in TypeScript (`@freedomofpress/sigstore-browser`, `hpke`), and its tests compare results with `@tinfoilsh/verifier` 1.3.0, a dev dependency only (`package.json:44-51`, README `:141-144`). Thinkr operates no enclave of its own.

| Route | hardware | recipient | reply | code | downstream | updates | fail-closed |
|---|---|---|---|---|---|---|---|
| SDK / app → Thinkr proxy → Tinfoil router | VCEK→ASK→pinned Genoa ARK E (`src/amd/chain.ts:25-45`, `:47-66`); report signature E (`src/amd/index.ts:36-38`); debug, migration agent, committed firmware, TSME E (`src/amd/policy.ts:38-59`, `:65-85`, `:123-130`; all four TCB fields vs floor `:91-103`; VCEK SPLs = reported TCB `:106-112`); TCB floor E but low: SNP SPL `0x0e` (`src/config/amd.ts:44`); Genoa only; no VCEK CRL check (not found) | EHBP (HPKE X25519) to the key in REPORTDATA[32:64], E (`src/amd/index.ts:43-49`, `src/ehbp/fetch.ts:61-62`); TLS cert must carry the attested TLS key, HPKE key and attestation hash, E (`src/enclave/certificate.ts:37-52`), though the SDK's TLS goes to Thinkr, not the enclave | response frames AEAD-authenticated under keys derived from the request's HPKE context, E (`src/ehbp/response.ts:38-53`, `:75-94`); a non-2xx without the EHBP nonce passes through unauthenticated (`src/ehbp/fetch.ts:87-94`); no per-reply signature | Sigstore DSSE against pinned trusted root, OIDC issuer GitHub, workflow repository = repo, ref must be a tag, E (`src/code/release.ts:39-44`, `:57-63`); subject digest E (`:105-115`); measurement = release `snp_measurement` E (`src/verify.ts:58-60`); any signed tag accepted, no workflow-file pin (README `:124-125`) | router→model enclave N: only the router is attested; the proxy forwards ciphertext to any HTTPS `*.tinfoil.sh` origin the client names (`thinkr-proxy/src/tinfoil/sealed.ts:97-105`) | auto-adopts any newly signed router tag | SDK: refuses on any step failure; no plaintext fallback for private models (`thinkr-sdk/src/sealing.ts:46-59`, `src/enclave.ts:32-42`); `zdr/` and `open/` model ids go plaintext by the caller's choice (`src/config/api.ts:29-35`, `src/sealing.ts:38-44`) |

Notes:

- **TCB floor below the AMD-SB-3037/3038 fix.** The floor `{bootloader 0x07, tee 0x00, snp 0x0e, microcode 0x48}` is copied from tinfoil-js 1.3.0 (`src/config/amd.ts:34-44`). Thinkr's own fixture of the live router on 2026-10-23 reports SNP SPL `0x17` in current, reported, committed and launch TCB (bootloader `0x0a`, microcode `0x54`; decoded from `test/fixtures/router-bundle-2026-10-23.json`). Both the floor and the router as of that date are below the Genoa fix level `0x1D`. The verifier would pass that router.
- **Nonce/freshness: N.** The report carries only the TLS fingerprint and HPKE key in REPORTDATA (`src/amd/index.ts:9-11`); no client nonce. The VCEK is checked for validity on the current date only (`src/amd/chain.ts:63`). The SDK caches a passed verification for 15 minutes or until the certificate expires, and re-verifies early when the enclave answers with the EHBP key-configuration problem (`thinkr-sdk/src/config/verification.ts:13`, `src/session.ts:33-36`, `:54-58`, `src/sealing.ts:56-59`).
- **Bundle source.** The default path fetches the bundle through Thinkr (`thinkr-sdk/src/enclave.ts:44-48`) or `chat.thinkr.sh` (`src/config/sources.ts:10`); every field is checked against AMD and Sigstore, so the relay can withhold but not forge [i]. `--enclave` builds it from the enclave, GitHub and AMD KDS directly (`src/bundle.ts:88-114`), and takes the latest GitHub release digest (`:116-125`).
- **Where plaintext exists.** SDK/browser and inside Tinfoil's router; the router decrypts and forwards to model enclaves that the client never appraises. The proxy sees model, size, timing and token counts (`thinkr-proxy/README.md:16-21`). Open/ZDR lanes are plaintext at the proxy and OpenRouter (`README.md:22-28`).
- The chat web app's own verifier code is not in any public thinkrsh repo (`gh repo list thinkrsh`: issuer, sdk, proxy, contracts, verifier, sync). The proxy README says the browser verifies first (`README.md:16-17`); not checked.
- Audio, document and privacy-filter routes were not reviewed beyond the proxy route list (`thinkr-proxy/src/routes/private.ts:1-9`); the filter is verified against `tinfoilsh/confidential-pii-cpu` as a separate enclave (`src/config/tinfoil.ts:24-30`).

## 2. Ritual: attestation is checked on-chain by the network, not by clients

### ritual-judge-protocol

The relayer is the only client. It reads executors from Ritual's `TEEServiceRegistry.getServicesByCapability(LLM, checkValidity=true)` and keeps those with `isValid` (`relayer/src/relayer.ts:205-219`), calls `HermesRitualLLM.ask(executor, prompt)` on Ritual (`:282`), reads the result, and posts three scores plus three Ritual tx hashes to Arc, where `AIJudgePanel` takes the median (`src/AIJudgePanel.sol:146-167`). Nothing in the repo parses a quote, a key, a signature or a measurement.

| Route | hardware | recipient | reply | code | downstream | updates | fail-closed |
|---|---|---|---|---|---|---|---|
| relayer → HermesRitualLLM (0x0802) on Ritual → Arc panel | delegated to Ritual registry `isValid`: N in client | N: the prompt is public calldata in `ask()` (`relayer.ts:282`) | result read from contract storage as `inferences(inferenceCount-1)` (`:286-290`); no signature check; Arc trusts the relayer (`AIJudgePanel.sol:150`, `onlyRelayer`) | N in client; registry `workloadId` not read | executor→model endpoint N | registry-driven | throws if <3 valid executors unless `ALLOW_EXECUTOR_REUSE` (`relayer.ts:221-241`); `EXECUTOR_ADDRESSES` env skips the registry and its `isValid` filter (`:207-209`) |

Weaknesses:

- **Wrong-result race [i].** The relayer takes "the latest inference id" as `inferenceCount() - 1` after its own tx (`relayer.ts:284-290`). Another caller's `ask()` in between would make it score someone else's answer, if `HermesRitualLLM` assigns ids by a shared counter (erhnysr/hermes-ritual-bridge not read). The stored Ritual tx hash would still be the relayer's own.
- **Relayer is trusted.** `submitScores` and `onAIJudgeResult` are `onlyRelayer` (`AIJudgePanel.sol:82`, `:150`, `:179`); the Arc contract cannot check that the scores match the tx hashes. The README's "no one has to trust the relayer's arithmetic" (README `:40-43`) covers only the median.
- DEBUG executors not excluded by the client: the relayer filters on `isValid` only and never reads `node.teeType` (`relayer.ts:66`, `:216`).
- No privacy: content and prompt are on-chain calldata.

### Ritual's own verification

- **Who verifies.** `ritual-net/ritual-sc-core` has only the registry interface. A TDX executor registers itself with `registerTdxExecutorWithPermit(teeAddress, …, tdxQuote, …, teeSignature)` (`src/async/ITEEServiceRegistry.sol:182`); "the flashtestation registry is the anchor of trust for all attestation validity checks" (`:141`). The Flashtestation submodule points at a private repo, `git@github.com:ritual-net/flashtestations-internal.git` (`.gitmodules`), and the policy interface imports Automata's on-chain DCAP types (`src/async/ITEECapabilityPolicy.sol:4-7`). So quote verification, TCB policy and workload allowlist live in contracts whose source is not public. `TeeType` includes `DEBUG` (`ITEEServiceRegistry.sol:17-20`); whether `isValid` excludes DEBUG nodes: not found.
- **Results.** The Ritual node ("Ritual reth checks the executor is valid at job commitment") and `AsyncJobTracker` re-check `getValidService` at settlement (`src/async/AsyncJobTracker.sol:420-428`). Ritual's docs say "every result is signed with the executor's TEE attestation key. The chain verifies this" (`ritual-dapp-skills/skills/ritual-dapp-overview/SKILL.md:380`). Clients trust chain consensus.
- **Registry ≠ binary.** Ritual's own docs: "Registry membership alone does not prove which binary a TEE runs" (`skills/ritual-dapp-http/references/rithttp1-private-io.md:14`), and, for the RITHTTP1 HTTP route, "the upstream provider sees request plaintext" (`:16`). The LLM precompile calls "whatever inference endpoint the executor actually talks to" (`skills/ritual-dapp-llm/SKILL.md:74`); conversation history is plaintext JSONL on GCS/HF/Pinata (`:10`, `:60`).
- **No public client-side verifier found.** GitHub org listings: ritual-net has one public repo (ritual-sc-core), ritual-foundation one (ritual-dapp-skills). Code search for `TEEServiceRegistry attestation` found only third-party apps. 0xheycat/Purrcha's `/api/verify` fetches the receipt and decodes `spcCalls` output (`src/app/api/verify/route.ts:32-70`); it says "Ritual does not expose a separate attestation blob in the receipt today" (`:90`), and its UI labels attestation "implicit" via the registry (`src/components/ritual/VerificationDrawer.tsx:305-307`).

### Tally

- 6 of 9 touch NEAR AI attestation (Veil, nearly-estate, Styx, tanat, secondeyes, lifeguard). sentinel-registry-near and aotrust-skills have no LLM path; hqBrimax/sentinel calls OpenRouter and labels a self-signed source hash "TEE attestation".
- 3 verify the TDX quote signature at runtime: Veil (SDK 0.3.0), nearly-estate (SDK 0.2.1) and Styx (own Python, dcap-qvl 0.7.1). secondeyes checks it only in an offline script before the owner pins a key. tanat and lifeguard never check it; tanat's status API still claims per-request quote verification.
- 3 block the prompt before sending: Veil, Styx and nearly-estate (through the SDK's `fetch` [i]). secondeyes and nearly-estate also gate contract actions on an ed25519 signature under an owner-set key, after the prompt has gone out; neither contract sees a quote, and nearly-estate's owner script reads the key from the report with no check. tanat and lifeguard block nothing.
- Prompt hidden from the app server: Veil (browser, E2EE v3; the shared-key proxy sees ciphertext) and Styx (local). nearly-estate's server is the prompt author and runs in its own Phala CVM; it sends v2 E2EE for swarm calls and plaintext for judge calls. tanat's Worker sees plaintext.
- dcap-qvl 0.7.0 reaches Veil and nearly-estate through the published SDK builds (0.3.0 and 0.2.1 both pin it), and secondeyes's offline script pins it directly. Styx resolves 0.7.1. OutOfDate is accepted by Veil (default mode), nearly-estate (SDK default, plus TDRelaunchAdvised) and Styx.
- Styx decodes the NRAS JWT without a signature check, as NEXORA and antrepreneur do, and accepts any one passing model candidate, as pixlz does. Its MRCONFIGID check silently skips when `app_compose` is absent. No app here reads stored event-log digests on its own; both SDK builds recompute them.
