# Client comparison, part I: agent plugins (pi-tee, pi-privacy, opencode-tinfoil) and tinfoil-cli

Source review only. Nothing was built, installed or run; no unit tests were run, because each repo needs an npm or Go module install first. Pins: ariofrio/pi-tee `64e86da` (2026-11-07), privateer-agent/pi-privacy `93adf50` (2026-09-12), rndmcnlly/opencode-tinfoil `0bb3d3d` (2026-10-12), tinfoilsh/tinfoil-cli `97c76a7` (2026-11-12). Two plugins delegate to vendor SDKs, so the SDKs were read from their npm tarballs at the versions in each lockfile: `tinfoil@1.2.1` + `@tinfoilsh/verifier@1.2.1` + `ehbp@0.3.2` (opencode-tinfoil), and `@nearai/inference-sdk@0.1.0` (pi-tee NEAR).

Cells and legend as in part A: **E** enforced (failure blocks the send or the reply), **C** checked, not enforced, **N** not checked, **n/a**. `[i]` = inferred. teep comparisons refer to part A §1.

## 1. pi-tee (Pi extensions: NEAR, Tinfoil, Chutes, Privatemode)

Path keys. `C/` = `packages/core/src/`, `N/` = `packages/nearai/src/`, `T/` = `packages/tinfoil/src/`, `G/` = `tools/tinfoil-public-build/`, `SDK` = `@nearai/inference-sdk@0.1.0 dist/node.js` (the bundle `N/` imports).

pi-tee maps each route onto levels: code A1-3, host H1-3, GPU G1-3, egress X1-3. It admits a route only if every level meets the policy (`C/security.ts:48-90`). The default policy `public-builds,egress=metadata` (`C/policy.ts:26`) needs A1, H1 and G1, so it admits only the Tinfoil direct-worker and billing-gateway routes. NEAR, the Tinfoil router and Chutes are code A3, and are admitted only under `trust-provider-and-host`. That position defaults to `host=stale,gpu=unchecked` (`C/policy.ts:70-74`). Every request opens a new session: fresh nonce, new appraisal, one owned socket, one send (`C/provider.ts:280`, `T/direct.ts:37`). Every Tinfoil appraisal expires 60 s after it is checked (`T/worker-appraisal.ts:93`). The opt-in `appraisal=reuse` keeps one for later requests until that expiry, without a fresh challenge (`T/public-session.ts:15-16,80-98`). NEAR sessions expire 300 s after the challenge (`N/gateway.ts:71`, `N/direct.ts:77`). Runtime reuse: NEAR's `@nearai/inference-sdk`, `@phala/dcap-qvl`, tinfoil-go `23734b7` inside the WASM helper, and `ehbp`. The `tinfoil` npm SDK appears only in `scripts/research/`. It cites teep in its provider survey (`docs/evidence/providers/2026-10-08-survey.md:158,191`).

**vs teep.** *Tinfoil: stronger.* teep attests only the router, with router code from the latest release and backend N. pi-tee appraises the model worker itself: fresh nonce, local GPU appraisal, model release and container chain, and a higher SNP floor. *NEAR: weaker.* With no MRTD, compose or app-id pin, any genuine dstack TD with a matching binding passes as the model. GPU is never gated, and the default `host=stale` accepts OutOfDate; teep enforces MRTD, compose, GPU and TCB. The model-signature check before delivery is stronger than teep's content N, but it only authenticates a key held in an unpinned TD. Both send E2EE v2.

## 2. pi-privacy (Pi extension: privacy badge, PII gate)

Path keys. `A` = `src/attest/attestation.ts`, `D` = `src/attest/dispatcher.ts`, `X` = `src/extension.ts`, `PV` = `src/posture/verify.ts`, `TI` = `src/posture/tiers.ts`. Only dependency: `undici` (`package.json:71-72`). No SDK, no quote library.

| Provider | hardware | recipient | reply | code | downstream | updates | fail-closed |
|---|---|---|---|---|---|---|---|
| nearai | **N.** Fetches `/v1/attestation/report` with a 32-byte nonce (`A:80-110`). "Verified" means a string named `signing_address` exists, the JSON text contains "nvidia\|gpu" or "intel\|tdx", and the nonce appears anywhere in the JSON (`A:114-138`). The file says it does no quote check (`A:37-40`). Green needs the address, the nonce, and one hardware marker (`A:118-121,137`) | N: Pi's plain OpenAI-compatible provider to `cloud-api.near.ai` over WebPKI (`src/ext/register.ts:28-53`); no E2EE anywhere (grep) | N | N | N | n/a | fail-open |
| tinfoil | **N.** Reads `report_data[0:32]` at offset 0x50 of the gunzipped report and compares it with the SHA-256 of the TLS leaf SPKI. AMD signature, chain and measurement are not checked (`A:144-149,262-273`). For any format, the SPKI hash appearing anywhere in the report bytes also counts as a match (`A:269-272`) | TLS SPKI captured from the first connection per host and never refreshed (`D:26,43`); inference connections are not pinned. No EHBP | N | N | router only [i] | n/a | fail-open |

- **Fail-open.** Posture is computed asynchronously on `model_select` (`X:435,463`) and never gates `before_provider_request` (`X:467-486`). Attestation only colors the badge and feeds two prompts that default to `warn` (`X:85,96`).
- **A false green weakens the client.** `tee-verified` turns off the PII gate (`X:65-66,486`). Anyone who can serve a JSON document with the right strings (NEAR), or a report blob containing their own SPKI hash (Tinfoil), gets green and skips the gate.
- **Labeling.** `TI:44-46` calls green "cryptographically verified: remote attestation proved genuine TEE hardware", while the README calls these "pragmatic checks ... not a replacement for a full verifier" and points to nearai/cloud-verifier and tinfoil-cli (`README.md:578-581`).
- **Freshness.** NEAR's nonce is per posture refresh, not per request. Tinfoil has no nonce.

**vs teep: weaker on both providers.** No signature verification of any kind.

## 3. opencode-tinfoil (OpenCode provider plugin)

Path keys. `I` = `src/index.ts`, `PV` = `src/provider.ts`, `V2` = `src/v2.ts`. SDK, at the exact pin `tinfoil: "1.2.1"` (`package.json:50`): `SC` = `tinfoil@1.2.1 dist/secure-client.js`, `ATC` = `dist/atc.js`; `VC` = `@tinfoilsh/verifier@1.2.1 dist/client.js`, `VA` = `dist/attestation.js`, `VS` = `dist/sigstore.js`, `VV` = `dist/sev/validation.js`, `VCC` = `dist/sev/cert-chain.js`, `CV` = `dist/cert-verify.js`; `EH` = `ehbp@0.3.2 dist/esm/client.js`.

The plugin is a thin wrapper. It routes every OpenCode inference body through `SecureClient.fetch` (`PV:14-31,49-59`), removes unmarked or unsupported candidates (`V2:22-25`), and defaults to EHBP (`I:71`). The SDK is **tinfoil-js, not tinfoil-go**, so part B §3 does not carry over.

|---|---|---|---|---|---|---|---|
| default (`inference.tinfoil.sh`, router) | SNP only, Genoa only (`VCC:36-37`); ARK/ASK embedded (`VCC:42-43`); **no CRL check** (no `crl`/`revoc` in the verifier). Floor hard-coded at snp 0x0E / ucode 0x48, build 21, debug and MA off (`VV:8-36,71-72`), all E. GPU N. **No nonce**: the bundle comes from an ATC GET with no challenge (`ATC:10-28`), and `report_data` is TLS-fp ‖ HPKE key (`VA:40-41`) | EHBP to the HPKE key in `report_data` (`SC:238-247`); the cert SAN must carry the same HPKE key and the attestation hash (`CV:93-124`). `transport: "tls"` pins the SPKI instead | EHBP: a 2xx without `Ehbp-Response-Nonce` is rejected; non-2xx passes through in plaintext (`EH:92-101`) | Sigstore DSSE from `tinfoilsh/confidential-model-router`, any `refs/tags/*` workflow (`VS:52-57`), digest == ATC-supplied digest (`VS:82`). - **Freshness and caching.** Verified once per `SecureClient` and cached for the life of the process (`SC:126-144`). It re-attests only on an EHBP key-config mismatch (`SC:276-279`) or an explicit `reset()`. There is no freshness witness and no TTL.
- **Reuse.** Entirely the Tinfoil JS SDK; no checks of its own. It does not cite teep or tinfoil-go.

**vs teep: similar.** Same router-only scope and auto-adopted router code. The JS SDK enforces the AMD chain, where teep lets it fail (part A, `R:649-650`). It is weaker on freshness: no challenge, no CRL, and a process-lifetime cache against teep's 1 h. Whether teep sends a nonce on Tinfoil was not checked. A stale bundle buys acceptance of an old TCB or a retired release. It cannot substitute a key, because EHBP still encrypts to the key in the report. With `enclaveURL` + `configRepo` (`I:15-17`, `SC:102-107`), the SDK verifies a named enclave against a named repo.

## 4. tinfoil-cli (`tinfoil attestation verify`, `tinfoil http`, deprecated `tinfoil proxy`)

Path keys. `cli/` = `internal/cli/`, `conn/` = `internal/connection/`. Verification is tinfoil-go **v0.17.0-rc.8** (`go.mod:21`). Part B §3 read rc.9. rc.9 adds SNP report and TDX collateral-shape tightenings (#306, #307) on top of rc.8. The TLS-pin default `a8c8ab9` is already in rc.8. Container, bunker and SSH commands were out of scope; the `trust.json` known-configs gate applies to controlplane-resolved container configs, not to these commands (`cli/policy_gate.go:15-19`).

**vs teep: similar** on the router. Both auto-adopt the router release, and neither attests the model enclave by default. tinfoil-go enforces the AMD chain, where teep lets it fail on KDS outages (part A, `R:649-650`). Explicit `--repo …@sha256` gives a pinned release and direct model-enclave verification, which teep's Tinfoil row lacks.

## Differences that matter most

- **Only pi-tee attests a Tinfoil model enclave in the default path.** tinfoil-cli (`--enclave`/`--repo`) and opencode-tinfoil (`enclaveURL`/`configRepo`) do so only when configured. teep and the gateway stop at the router.
- **Only pi-tee holds a NEAR reply until its signature verifies.** That closes reply forgery on NEAR, which teep leaves at N. pi-tee still uses E2EE v2, so a gateway that swaps the reply key can read the reply before the signature check fails it [i].
- **pi-tee's NEAR verifier, NEAR's own inference-sdk 0.1.0, recomputes dstack event digests from payloads.** It avoids the `verifier-ts`/abalone bug class. It does not read `compose_manager_attestation` and has no compose pin unless the caller supplies a deployment verifier, and pi-tee supplies none.
- **The JS Tinfoil SDK is weaker than tinfoil-go.** It has no nonce, no CRL and no TTL, so anything built on `tinfoil@1.2.1` (opencode-tinfoil) inherits an unchallenged, process-lifetime verdict.
- **pi-privacy verifies no signatures.** Its green badge also disables its own PII gate.
