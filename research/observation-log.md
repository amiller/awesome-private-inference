# Observation log: TOFU-and-complain, as a civic audit

Status: design note. Goal — document the thinking and propose a concrete way to
log it, grounded in what this repo already collects.

## The problem: a pinned verifier is doing TOFU

Every client-side confidential-inference verifier ends up pinning *something* —
a KMS root, a workload id, an image/compose digest (e.g. bitrouter's
`AciDcapVerifierPolicy::new(workload_ids, image_digests, kms_roots)`, a flat
off-chain allowlist supplied by env). Whoever wrote the allowlist is trusted, and a
legitimate provider upgrade either breaks verification or requires hand-editing the
list from a feed you also have to trust. That is trust-on-first-use. Plain TOFU does
not remove trust; it relocates it to "the first value I happened to see," with no way
to catch a MITM or a silent stack-swap after the fact.

This is not hypothetical here: on 2026-05-05 a `model_name` check caught a **live
silent gateway substitution** (`deepseek-ai/DeepSeek-V3.1` → `Qwen/Qwen3.5-122B-A10B`)
on a NEAR backend. The only reason it was caught is that we had a prior observation to
compare against.

## The principle: TOFU-and-complain + a civic duty to chip in

You can't avoid accepting *something* on first contact. But you can refuse to do it
blindly and silently:

1. **Cross-check, don't just trust.** Compare the observed pin against an independent
   authority — for NEAR, the on-chain `addComposeHash` set on Base, which this repo
   already sweeps (`data/near-onchain-set-2026-05-07.json`,
   `data/onchain-status.json`). An observation that is *currently authorized on-chain*
   is categorically different from one that is merely first-seen.
2. **Complain, never silently pass or fail.** When a pin changes versus last-seen, or
   diverges from the on-chain authority, surface it loudly ("the box changed its stack
   since you pinned") instead of letting it ride because it still matches a stale
   allowlist, or failing closed with no explanation.
3. **Chip in (the civic part).** Verification is a public good. A verifier that
   free-rides on blind TOFU weakens everyone's. Publish each signed observation to a
   shared, append-only log so drift and gateway-substitution are caught *collectively*
   — the way Certificate Transparency turned "trust this CA" into "every issuance is
   publicly monitorable."

## What this repo already has (build on it, don't rebuild)

- **Observation capture** — `data/snapshots/<date>.json`, one row per provider×model
  with `signing_address`, `details.gateway_compose_hash`, `cloud_api_image_digest`,
  `chain_authorized` (`probes/collect.py`, schema in `data/schema.json`).
- **The independent authority** — `probes/onchain_sweep.py` reads Base and records each
  authorized `compose_hash` with `first_seen_block / first_seen_timestamp /
  first_seen_date`. That is exactly the continuity primitive we need, already present
  for the on-chain set.
- **A static anchor** — `hermes_anchor_url` pins the allowed set for closed-chain
  clients.

The gap: snapshots are independent daily files. There is no first-class, per-target
*continuity record* that diffs each observation against the prior one and against the
chain, and no shared submission path. Drift is catchable but only by hand.

## Proposal: a continuity log + a complaint feed

Two derived artifacts, both regenerated by the daily probe from the snapshot stream +
the on-chain set. No new trusted infrastructure.

### 1. `data/continuity/<provider>/<model>.json` — per-target history

```json
{
  "provider": "near-ai",
  "model": "openai/gpt-oss-120b",
  "current": {
    "compose_hash": "a986df43…",
    "image_digest": "23ee3d3e…",
    "signing_address": "0x56d070…",
    "onchain_authorized": true
  },
  "first_seen": "2026-04-23",
  "last_seen": "2026-06-18",
  "changes": [
    { "date": "2026-05-05", "field": "served_model",
      "old": "deepseek-ai/DeepSeek-V3.1", "new": "Qwen/Qwen3.5-122B-A10B",
      "onchain_authorized": false, "severity": "high",
      "note": "silent gateway substitution" },
    { "date": "2026-05-08", "field": "compose_hash",
      "old": "…", "new": "95cbf0a8…",
      "onchain_authorized": true, "severity": "info",
      "anchor": "addComposeHash @ Base block 45726790" }
  ]
}
```

`severity` is the whole point of "complain": a change that is **authorized on-chain**
is `info` (a legitimate, governed upgrade); a change that is **not** in the on-chain
set is `high` (the thing you actually want to know). This is the cross-check from
principle (1) made mechanical — last-seen continuity *and* live authority, together.

### 2. `data/complaints.json` — the machine-readable alert feed

Just the `severity >= warn` changes across all targets, newest first, so a consumer
(or a CI gate, or a chat client) can subscribe without diffing the whole log. This is
the "complain" output other tools consume.

### 3. Tamper-evidence — signed daily checkpoint

Each run appends a checkpoint: `head = sha256(prev_head ‖ canonical(today's
observations))`, written to `data/checkpoints.jsonl` and signed. A hash-chained head
(plus the existing signed-commit git history) makes the log append-only and
externally auditable — a monitor that saw yesterday's head can prove today's didn't
rewrite history. Cheap; no Merkle tree needed at this scale.

### 4. "Chip in" — third-party submissions

A submission is one `attestationRow` + a signature over its canonical form + the
observer's identity. Start with the lowest-friction venue we already have: a PR adding
the signed row under `data/submissions/<observer>/<date>.json`; CI verifies the
signature and folds it into the continuity log, attributing the observer. So a
substitution seen by *anyone* — not just this repo's CI from one network vantage — is
recorded. (A submission endpoint or riding bitrouter's P2P registry are later, lower-
friction venues; the format is the same.)

## What ships first

The smallest useful slice is **(1) + (2)**: derive the continuity log and complaint
feed from the snapshots and the on-chain set already on disk. That turns the
substitution we caught by hand on 2026-05-05 into something the daily run catches and
publishes by default — and it's the reference the bitrouter pin-provenance proposal
(T1 + drift signal) can point at as a working consumer.

## Relation to bitrouter

bitrouter is a *client* verifier that today pins a flat off-chain allowlist. This log
is the *substrate* it could read instead of (or alongside) its env pins: cross-check
its pin against the continuity log's on-chain-authorized `current`, and contribute its
own observation back. Same idea on both ends — read the authority, complain on drift,
chip in.
