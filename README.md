## What this is

Private AI inference is a growing category. Providers claim "your prompts stay encrypted end-to-end inside a TEE." Some of them even expose `/attestation` endpoints you can verify. This repo:

1. **Re-verifies the attestation bundles daily.** Intel TDX quote → Phala verifier. NVIDIA GPU payload → NRAS. Signing key derivation → eth-keys. Nonce binding → report_data layout check.
2. **Sweeps pricing across overlapping catalogs.** Compare list and subscription prices for models available from more than one provider.
3. **Publishes a neutral scorecard** of which verification layers each provider actually delivers — and which they skip.
4. **Points at devproof-style gap analysis** so ✅/❌ aren't confused with "private" vs "not private."

## What "private inference" would mean

A prompt should be observable only to:
- The sender (the user / the agent).
- Code that is **attested**, **reproducible from source**, and **bound** to the public key the prompt was encrypted to.

A complete proof therefore requires:

| Layer | What's checked |
|---|---|
| **TDX quote** | Intel's DCAP verifier accepts the enclave quote; TCB is current. |
| **GPU attestation** | NVIDIA NRAS returns `PASS` for the claimed GPU, bound to the same nonce. |
| **Report-data binding** | The TDX `report_data` cryptographically commits to `(signing_address, nonce)`. |
| **Key derivation** | `signing_address` is derivable from `signing_public_key` (keccak of uncompressed pubkey last 20 bytes). |
| **Compose-hash commitment** | The enclave's `mr_config` contains the sha256 of the running docker-compose, so the image is auditable. |
| **Backend attestation** | If there's a gateway → backend hop (e.g. NEAR cloud-api routing to model CVMs), the gateway must verify the backend's quote — not just forward it. |
| **Channel binding** | The client verifies that the TLS SPKI or application-encryption key it uses is bound to the attested workload. |
| **Attested session** | An aggregator identifies the verified upstream channel, claims, and evidence used for this request. The client recomputes the session's content address. |
| **Receipt** | A key in the attested workload keyset signs the request, route, upstream session, and response hashes. |
| **Catalog → served** | The model the catalog advertises actually returns 2xx on a chat completion. |

A ✅ row in this registry means **only the layers we could automate**. The gaps are documented in every provider page.

## Known limitations

These are the reasons **no current provider is a complete end-to-end private inference solution**. They come from [amiller/devproof-audits-guide](https://github.com/amiller/devproof-audits-guide):

- **NEAR's gateway-side gap is N/A under closed-chain verification.** cloud-api PRs [#485](https://github.com/nearai/cloud-api/pull/485) / [#513](https://github.com/nearai/cloud-api/pull/513) / [#552](https://github.com/nearai/cloud-api/pull/552) / [#558](https://github.com/nearai/cloud-api/pull/558) (Mar–Apr 2026) deleted the operator-controlled discovery URL and now inline-verify each backend's TDX/RTMR3/NRAS before serving. `ALLOWED_COMPOSE_HASHES` is still unset on cloud-api — any TCB-current TDX TD the operator points the gateway at would pass server-side checks — but a closed-chain client extracts `compose_hash` from the attestation itself and checks it against the on-chain `addComposeHash` set on Base. Reference impl: [`verifiers/near_ai_lightclient.py`](./verifiers/near_ai_lightclient.py) (Block A + on-chain anchor + inner-compose pin) and [hermes-agent #12201](https://github.com/NousResearch/hermes-agent/pull/12201) (strict-mode static anchor pinning `(model → app_id, compose_hashes, os_image_hash, kms_pubkey)` plus inner-compose closure via `compose_manager_attestation.actions[]`). The model-name check on the latter caught a live silent gateway substitution on 2026-05-05 (`deepseek-ai/DeepSeek-V3.1 → Qwen/Qwen3.5-122B-A10B`). The DstackKms / DstackApp implementations on Base were unverified anywhere as of early May; we submitted the source and they now have `exact_match` on Sourcify, Basescan, and Blockscout (`Dstack-TEE/dstack@771f3c9e`). Three audit-driven NEAR PRs merged this month address remaining sharp edges: [`cvm-compose-files#30`](https://github.com/nearai/cvm-compose-files/pull/30) (HF weight pinning, live), [`compose-manager#11`](https://github.com/nearai/compose-manager/pull/11) (action-log persistence, awaiting next compose rotation), [`nearai-cloud-verifier#25`](https://github.com/nearai/nearai-cloud-verifier/pull/25) (verifier docs). `DstackKms.kmsInfo` is still empty on chain; closed-chain clients pin `info.key_provider_info.id` directly across attestations, so populating it would be belt-and-suspenders. Full trace: [DEVPROOF-REPORT-revisit-2026-05-02](https://github.com/amiller/devproof-audits-guide/blob/near-ai-inference/case-studies/near-ai-private-inference/DEVPROOF-REPORT-revisit-2026-05-02.md).
- **Current RedPill uses ACI and scores Stage 0.** On 2026-08-13, the official `aci` client verified the TDX quote, nonce-bound workload keyset, keyset freshness, RTMR3-bound Compose, and live TLS SPKI at `tee.redpill.ai`; it skipped key-custody policy. The new `--require-production-os` appraisal rejected the live dev-image hash. A paired run of the exact dstack-verifier digest pinned by the deployment returned `is_valid: true` and `os_image_hash_verified: true`, binding that hash through MRTD and RTMR0-2; a separate validation of dstack's published archive classified it as 0.5.9 with `is_dev: true`. That 5/6 protocol result is not an ERC-733 verdict. Against this repo's linked seven-part Stage 1 checklist, only auditable source was demonstrated. The measured deployment uses `dstack-dev-0.5.9`, permits an operator-supplied root SSH key, makes logs public while enabling raw upstream error detail, leaves source-to-image provenance unreproduced, and keeps active routing in operator-mutable state outside the measured Compose. All current Compose images are now digest-pinned, including the dstack verifier. Session pinning and receipts constrain and expose route choice, but the audit did not exercise a receipt and the root/log paths are independently disqualifying. A repeated session audit accepted 192 of 327 records; all 135 Chutes records failed. See [RedPill](./providers/redpill.md) and the [refresh audit](./research/redpill-phala-refresh-2026-08-12.md).
- **Chutes' in-enclave code and model are unmeasured — a verified quote ≠ verified code/model.** Chutes (Bittensor subnet 64, a custom non-dstack TDX stack) has a sound, live-verified crypto core: genuine non-debug TDX, ML-KEM-768 E2E key hardware-bound via `report_data[0:32]==SHA256(nonce‖e2e_pubkey)`, NVIDIA NRAS, and a *contained* (not trusted) miner host. But the operator-authored `serve.py`/`/app/chute.py` that decrypts the prompt is CFSV-excluded (`cfsv_wrapper.py:54`) and in no RTMR, and `model_name`/`revision` are never bound to the quote — so a passing attestation proves "genuine TDX+GPU running *a* Chutes base image," not which model on which code. Cross-user prompt exfiltration from a `verified=True` enclave was demonstrated live (2026-06-16/17). Two adjacent gaps: the default `llm.chutes.ai` path handles prompts in plaintext at the control plane (the E2E path is opt-in), and verify-then-encrypt is optional with no shipped client verifier. Filed as [chutesai/chutes#75](https://github.com/chutesai/chutes/issues/75) (measure the serving code) and [chutesai/e2ee-proxy#3](https://github.com/chutesai/e2ee-proxy/issues/3) (verify the e2e key against the quote). Full audit: [chutes-confidential-inference case study](https://github.com/amiller/devproof-audits-guide/tree/main/case-studies/chutes-confidential-inference).
- **`private-ai-verifier` is an attestation adapter, not Phala's whole client story.** At commit [`51c2b5a`](https://github.com/Phala-Network/private-ai-verifier/commit/51c2b5a83d6d753b9a29288e0ed522ab2d65bac4), the library still has no end-user E2EE or receipt flow, and its NVIDIA and Intel Trust Authority helpers decode JWTs with `verify_signature=False`. The newer ACI clients add native DCAP verification, attested TLS or E2EE keys, verified-route constraints, sessions, and receipts. Those additions do not cure the adapter's unsigned-JWT paths. They did allow the live PhalaDirect sessions to pass their integrity audit; the Chutes adapter records still failed. Updated boundary: [Phala](./providers/phala.md).
- **Skill-text backdoor.** Agent skill catalogs can silently skip every TDX-verification step while advertising `supportsE2EE`. Canonical example: [`veniceai/skills`](https://github.com/veniceai/skills) misnames the protocol, cites a 404 URL, and teaches none of the six verification steps — see [venice-private-inference case study](https://github.com/amiller/devproof-audits-guide/blob/main/case-studies/venice-private-inference/DEVPROOF-REPORT.md). Third-party proxies now do the verification the catalog omits, but an agent loading Venice's own skill still gets the bad guidance: `veniceai/skills` last shipped 2026-07-29 with nothing touching E2EE, and `docs.venice.ai/e2ee` still 404s.
- **Our own bar was wrong for Venice, and an outsider found it.** Venice's required-layer set excluded `prod_os_image` and `serving_code_attested` — the two layers where its prompt-path exposure actually lives — on the grounds that the backend belongs to NEAR/Phala. That made Venice the only full row on the dashboard until [an independent audit](https://github.com/jooray/venice-e2ee-proxy/blob/main/docs/SECURITY-AUDIT.md) pointed at exactly those two. Corrected 2026-08-10; Venice now reads 6/9. The general fix — deriving each bar from provider claims rather than from what the API happens to expose — is [#6](https://github.com/amiller/awesome-private-inference/issues/6), and the post-mortem is [#11](https://github.com/amiller/awesome-private-inference/issues/11).
- **KMS verification is still incomplete for the public ACI client.** The current RedPill/Phala ACI report publishes dstack KMS custody evidence, and the first-party upstream verifier can apply configured KMS-root policy. The public `aci verify` client still skips custody and subject policy. Evidence presence must not be scored as a pass.
- **Tinfoil's external-config disk (router-only on this deployment).** Tinfoil closes the Phala/NEAR compose-hash backdoor (the attested `/config.yml` is hardware-bound via `tinfoil-config-hash=` in the SEV launch-measured cmdline). The container schema permits env vars and secrets sourced from a *separate, unmeasured* disk at boot, but auditing each enclave on `inference.tinfoil.sh` (2026-04-26) shows: the model-router has 2 such slots (`DOMAIN`, `USAGE_REPORTER_SECRET`) which a code trace establishes are off the prompt path; the per-model enclaves where prompts actually run (gpt-oss-120b, llama3-3-70b, gemma4-31b — `deepseek-v4-pro`, `kimi-k2-6` were unreachable for direct probe) have **zero** string-form env entries and **zero** `secrets:` — fully attested. Full critique: [tinfoil-confidential-inference case study](https://github.com/amiller/devproof-audits-guide/blob/main/case-studies/tinfoil-confidential-inference/DEVPROOF-REPORT.md).

## Repo layout

```
awesome-private-inference/
  providers/*.md      one page per provider (claim / evidence / gaps / reproduce)
  verifiers/          attestation primitives — TDX, NRAS, per-provider shapes
  probes/             daily probe scripts + dashboard renderer
  data/snapshots/     JSON artifacts, one per CI run
  data/latest.json    symlink to most recent snapshot
  site/               (optional) extra static assets
  docs/               GitHub Pages output (generated)
  .github/workflows/  daily probe + page deploy + CI
```

## Run a probe locally

```bash
git clone https://github.com/amiller/awesome-private-inference
cd awesome-private-inference
uv venv && source .venv/bin/activate
uv pip install -e .

# Clone the NEAR AI verifier alongside (TDX primitives live there)
git clone https://github.com/nearai/nearai-cloud-verifier _nearai-verifier
export NEARAI_VERIFIER_PATH="$(pwd)/_nearai-verifier/py"

export NEAR_API_KEY=...        # optional
export VENICE_API_KEY=...      # optional

python -m probes.collect
# writes data/snapshots/YYYY-MM-DD.json + docs/index.html
```

## Adding a provider

Copy `providers/_template.md`, add a shape dispatcher in `verifiers/`, register it in `probes/attestation.py`. See [CONTRIBUTING.md](./CONTRIBUTING.md).
