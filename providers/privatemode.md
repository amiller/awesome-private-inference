# Privatemode: mutable manifest and client policy

**Status:** Candidate, publication and documentation review only. The [scoped audit](../research/review-2026-10-13/landscape.md) did not establish a live verified key exchange or model completion. Routes are in [`data/routes.json`](../data/routes.json).

The public [manifest](https://cdn.confidential.cloud/privatemode/v2/manifest.json) contains eight workload policies and SNP/TDX reference entries for a Coordinator, secret service, workers and an API. The current read-only capture is 5,992 bytes, SHA-256 `9f5ac6bf38431fb073c2185bd9b344140e776b4f7c32eee595716e9456bdec2a`, preserved with timestamp in [`data/references/latest.json`](../data/references/latest.json). A fetch proves only that this version was published and parseable; its measurement values, model roots and live enforcement have not been reproduced.

The [proxy configuration](https://docs.privatemode.ai/api/proxy-configuration/) describes two distinct policies. Its default mode fetches the latest provider manifest and may retry with it after a validation failure, logging the update locally. `--manifest-path` pins a locally reviewed manifest. The first mode can adopt a provider update; the second can reject it until review. The proxyless path has provider-side verification and, according to [trust documentation](https://docs.privatemode.ai/security/trust-and-compliance/), currently lacks client-side attestation. It needs a separate verdict.

Next, pin this exact manifest and client release; reproduce policy values on a suitable remote builder; inspect all Coordinator, secret-service, worker, egress, GPU and model-weight policies. With a pinned proxy, verify attestation/key exchange and a harmless encrypted completion, then mutate the manifest, workload policy, GPU verdict and mesh certificate to confirm rejection before payload release. Track automatic update and local-log behavior separately. No full private-inference claim follows from the current publication capture.
